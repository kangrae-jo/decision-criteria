# 아키텍처 의사결정 용어

- 출처: 사용자 제공 영상 요약
- 목적: 판단 기준을 작성하고 읽을 때 사용하는 공통 용어 정의

## 용어

| 용어 | 의미 | 예시·판단 |
| --- | --- | --- |
| 아키텍처 드라이버<br>Architecture Driver | 아키텍처 구조와 주요 설계 결정에 큰 영향을 주는 핵심 요인 | 동시 접속자 수, 법적 규제, 특정 기술 사용 제약. 단순한 기능 목록과 구분한다. |
| 품질 속성<br>Quality Attribute | 시스템이 기능을 얼마나 잘 수행해야 하는지를 나타내는 특성 | 성능, 가용성, 보안성. `피크 시간 요청의 95%를 1초 안에 응답`처럼 측정 가능하게 작성한다. |
| 아키텍처 택틱<br>Architecture Tactic | 특정 품질 속성의 반응을 개선하기 위한 설계 수단 | 성능을 위한 캐시, 가용성을 위한 중복 구성. 택틱 적용 자체보다 품질 속성 개선 여부가 중요하다. |
| 아키텍처 스타일<br>Architecture Style | 시스템 전체의 구성 요소와 상호작용을 조직하는 큰 구조 | Layered, Client-Server, EDA, MSA. 변경 영향이 넓으므로 개별 기능보다 신중하게 선택한다. |
| 아키텍처 패턴<br>Architecture Pattern | 반복되는 설계 문제와 맥락에 적용하는 재사용 가능한 해결 방식 | Cache-Aside, Circuit Breaker, CQRS, Saga. 일반적으로 스타일보다 적용 범위가 좁다. |
| 트레이드오프<br>Trade-off | 한 특성을 얻기 위해 다른 비용이나 제약을 부담하는 관계 | 캐시는 응답 성능을 높이지만 데이터 일관성과 운영 복잡도 비용을 만든다. |
| 아키텍처 의사결정<br>Architecture Decision | 드라이버와 대안의 트레이드오프를 비교해 내린 중요한 설계 결정 | 선택한 대안뿐 아니라 거부한 대안, 얻는 것과 감수하는 것을 함께 확정한다. |
| ADR<br>Architecture Decision Record | 특정 시스템에서 내린 아키텍처 의사결정과 맥락을 기록한 문서 | 상황, 결정, 대안, 근거, 결과와 후속 검증을 기록한다. |

## 용어의 관계

```text
Architecture Driver 식별
→ Quality Attribute를 측정 가능한 조건으로 구체화
→ Style·Pattern·Tactic 대안 비교
→ Trade-off 분석
→ Architecture Decision 확정
→ ADR로 기록
```

아키텍처 드라이버에는 기능 요구사항, 품질 속성, 기술·조직·법적 제약이 포함될 수 있다. 모든 요구사항이 드라이버인 것은 아니다. 구조에 유의미한 영향을 주는 항목만 드라이버로 다룬다.

택틱은 품질 속성을 개선하기 위한 수단이고, 패턴은 반복되는 문제의 해결 구조이며, 스타일은 시스템 전체의 큰 조직 방식이다. 실제 자료에서는 스타일과 패턴의 경계를 다르게 사용하기도 하므로 이 문서의 구분을 저장소 내부 정의로 사용한다.

## 판단 기준과 ADR의 구분

| 판단 기준 | ADR |
| --- | --- |
| 여러 프로젝트에서 재사용할 선택 기준 | 특정 시스템에서 실제로 내린 결정 |
| 조건별 대안과 트레이드오프 정리 | 당시 맥락, 선택한 대안과 결과 기록 |
| `어떤 조건에서 무엇을 선택하는가`에 답함 | `이 시스템에서 왜 이것을 선택했는가`에 답함 |

이 저장소의 `criteria/` 문서는 판단 기준이다. 특정 프로젝트에 기준을 적용해 실제 선택을 확정했다면 해당 프로젝트의 ADR로 별도 기록한다.
