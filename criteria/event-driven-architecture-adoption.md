# 이벤트 기반 아키텍처 도입 판단

- 상태: `adopted`
- 검토일: 2026-09-19
- 출처: 사용자 제공 영상 요약 — [Event-Driven Architecture가 필요하지 않을 때](https://www.youtube.com/watch?v=JLGNqi5g860)
- 주제: EDA, 도메인 이벤트, 동기 호출, 팬아웃, 일관성, 운영 준비
- 선택: 동기 직접 호출을 기본값으로 두고 필요한 경계에만 EDA 도입

## 결론

**채택: 완료된 비즈니스 사건에 소비자가 생산자의 응답과 독립적으로 반응해야 할 때 EDA를 도입한다.** 독립적 확장, 시간적 결합 제거, 장애 격리 중 적어도 하나가 [아키텍처 드라이버](../references/architecture-decision-terms.md#용어)여야 한다.

**유지: 단순 CRUD, 하나의 트랜잭션으로 지킬 불변식, 즉시 결과가 필요한 요청, 순차 의존성이 강한 워크플로우는 동기 호출과 명시적 파이프라인을 사용한다.**

**거부: Spring Modulith, MSA, Kafka 같은 도구나 구조를 사용한다는 이유만으로 이벤트를 도입한다.**

**보류: 이벤트의 비즈니스 의미, 실패 허용 범위, 중복·순서 처리와 운영 책임이 정해지지 않았다면 도입하지 않는다.**

## 적용 범위

이 문서에서 EDA는 완료된 사건을 발행하고 생산자가 소비자의 반응을 지시하거나 기다리지 않는 [아키텍처 스타일](../references/architecture-decision-terms.md#용어)을 뜻한다.

- 이벤트 사용과 비동기 처리는 같은 결정이 아니다.
- 인프로세스 이벤트만으로 분산 환경의 장애 격리와 시간적 분리를 얻지는 못한다.
- EDA는 MSA에만 적용되지 않으며, 이벤트 브로커 도입과도 별개의 결정이다.

## 빠른 기준

| 질문 | 판단 |
| --- | --- |
| 소비자의 처리 결과를 현재 요청에서 알아야 하는가? | 동기 호출 유지 |
| 하나의 로컬 트랜잭션으로 지켜야 하는 불변식인가? | 같은 트랜잭션에서 처리 |
| 완료된 비즈니스 사건에 소비자가 독립적으로 반응하는가? | EDA 후보 |
| 팬아웃, 부하 흡수 또는 장애 격리가 필요한가? | EDA 우선 검토 |
| 소비자 반영이 늦어지는 것을 허용하는가? | 허용할 때만 비동기 EDA 검토 |
| 하나의 소비자가 다음 단계 결과를 반환해야 하는가? | 직접 호출이나 파이프라인 우선 |
| 중복·순서 변경·재처리를 운영할 수 있는가? | 불가능하면 도입 보류 |
| 테이블 변경이나 CRUD 요청을 그대로 노출하는가? | 도메인 이벤트로 사용하지 않음 |

낮아진 결합도와 새로 생기는 일관성·실패·운영 비용의 [트레이드오프](../references/architecture-decision-terms.md#용어)를 경계별로 판단한다.

## 1. EDA 도입과 거부 조건

다음 조건이면 EDA를 적용한다.

- 생산자의 핵심 처리가 이미 완료됐다.
- 소비자의 성공이 생산자의 응답을 결정하지 않는다.
- 소비자 변경, 처리 속도와 장애를 생산자로부터 분리해야 한다.
- [품질 속성](../references/architecture-decision-terms.md#용어)의 일관성 요구가 최종적 일관성을 허용하고 계약과 운영 소유자가 명확하다.

다음 조건이면 동기 호출을 유지한다.

- 즉시 결과, 순차 실행 또는 전체 롤백이 필요하다.
- 하나의 Aggregate나 로컬 트랜잭션에서 불변식을 지킬 수 있다.
- 독립적으로 반응할 비즈니스 사이드 이펙트가 없는 단순 CRUD다.

예를 들어 좌석 중복 방지와 예약 확정은 하나의 일관성 경계에서 완료한다. 이후의 알림, 통계와 검색 색인 갱신은 `ReservationConfirmed`에 독립적으로 반응할 수 있다.

다음 사용은 거부한다.

- 비동기 방식이 더 현대적이라는 이유로 도입한다.
- 메서드 호출을 이벤트 이름으로 바꾸고 순차 의존성을 숨긴다.
- 하나의 트랜잭션으로 지킬 불변식을 여러 소비자로 분산한다.
- Exactly Once를 가정하고 중복 처리와 재시도를 설계하지 않는다.

## 2. 팬아웃과 일관성의 예외

여러 소비자가 같은 사건에 독립적으로 반응하는 팬아웃은 강한 채택 신호다. 그러나 1:1 통신도 느린 작업 분리, 순간 부하 흡수, 장애 격리나 재시도가 필요하면 비동기화할 수 있다. 즉시 결과와 순차 의존성이 필요하면 직접 호출을 유지한다.

강한 일관성이 필요한 규칙은 여러 비동기 소비자로 분리하지 않는다.

```text
로컬 불변식과 핵심 상태 변경
→ 소유 Aggregate의 트랜잭션에서 완료
→ 완료된 사건 발행
→ 독립적인 후속 작업은 비동기로 처리
```

분산 처리가 불가피하면 중간 상태, 타임아웃, 보상과 수동 복구를 정의한다. 순서와 상태를 중앙에서 통제해야 하면 Orchestration을, 소비자가 독립적으로 반응하면 Choreography를 검토한다. Saga 패턴은 분산 처리를 원자적으로 만들지 않는다.

DB 변경과 이벤트 발행의 원자성은 [DB 변경과 이벤트 발행 일관성](db-event-publication-consistency.md)에서 판단한다.

## 3. 도메인 이벤트 기준

| 구분 | 예시 | 판단 |
| --- | --- | --- |
| 도메인 이벤트 | `ReservationConfirmed`, `PaymentFailed` | 이미 발생한 비즈니스 사실 |
| 명령 | `ConfirmReservation`, `SendNotification` | 성공 여부가 정해지지 않은 수행 요청 |
| CRUD 알림 | `reservation_row_updated` | 물리 저장 구조의 변경 |
| CDC 레코드 | 테이블의 INSERT·UPDATE·DELETE | 데이터 통합에는 사용 가능하지만 도메인 이벤트와 구분 |

이벤트 이름과 payload는 유비쿼터스 언어를 사용한다. Entity나 테이블 전체를 노출하지 않고, 생산자가 계약과 호환성 정책을 소유한다.

## 4. 운영 준비

다음 항목을 운영할 수 없으면 분산 EDA 도입을 보류한다.

| 항목 | 최소 기준 |
| --- | --- |
| 전달 안전성 | 멱등 처리, 제한된 재시도와 영구 실패 구분 |
| 순서·재처리 | 보장 범위, 역전 허용 여부와 재처리 시작점 명시 |
| 실패 복구 | 실패 이벤트 보관, Dead Letter 또는 수동 복구 경로 확보 |
| 관찰 가능성 | eventId·correlationId 추적, 지연·적체·실패 측정 |
| 계약·소유권 | 호환성 규칙과 생산·소비·장애 대응 담당자 명시 |

멱등성은 핸들러 실행을 한 번으로 제한하는 것이 아니다. 중복 실행 후에도 외부에서 관찰되는 최종 효과를 같게 만드는 규칙이다.

## 아키텍처 트레이드오프

| 선택 | 얻는 것 | 부담하는 것 |
| --- | --- | --- |
| 동기 호출·파이프라인 | 즉시 결과, 명시적 순서와 단순한 트랜잭션 | 시간적 결합과 장애 전파 |
| 인프로세스 이벤트 | 작은 도입 비용과 모듈 간 알림 | 프로세스 장애 격리와 독립 배포 없음 |
| 분산 EDA | 시간적 분리, 독립 확장과 장애 격리 | 일관성, 계약, 중복·순서와 운영 비용 |

## 검증 방법

- 동기 흐름과 이벤트 흐름의 상태와 실패 지점을 비교한다.
- 중복 전달과 순서 역전 후 최종 상태를 확인한다.
- Consumer와 Broker 중단 후 적체, 복구 시간과 재처리 결과를 측정한다.
- 계약 변경의 하위 호환성과 eventId 기반 전체 흐름 추적을 확인한다.

## 최종 판단 기준

> 동기 호출로 요구사항과 일관성을 단순하게 지킬 수 있으면 유지한다. 완료된 비즈니스 사건에 독립적인 반응, 시간적 분리나 장애 격리가 필요하고 최종적 일관성을 허용할 때만 EDA를 도입한다. 도입 전 이벤트 계약, 중복·순서·재시도, 관찰 가능성과 운영 소유자를 확정한다.
