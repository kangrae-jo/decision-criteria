# Java `final` 키워드 사용

- 상태: `validated`
- 출처: Java 언어 규칙과 블랙잭 미션의 상속 제한 사례
- 주제: 재할당, 불변성, 상속, 프레임워크 프록시

## 결론

**채택: 재할당·재정의·상속이 요구사항이 아니라면 `final`을 사용한다.** 변경을 허용해야 할 이유가 생겼을 때 `final`을 제거하는 방향을 기본값으로 둔다.

**거부: `final`을 객체 불변성이나 스레드 안전성과 동일시하지 않는다.** `final` 참조가 가리키는 객체의 내부 상태는 여전히 바뀔 수 있다.

**거부: 성능 향상을 목적으로 `final`을 사용하지 않는다.** 성능 효과는 JVM 구현과 실행 시점 최적화에 따라 달라지므로 설계 기준으로 삼지 않는다.

## 빠른 기준

| 적용 대상 | 기본 판단 | 예외 |
| --- | --- | --- |
| 생성자에서 초기화한 필드 | `final` 채택 | 객체 생명주기 중 참조 교체가 실제 요구사항일 때 |
| 지역 변수 | 재할당하지 않으면 `final` 채택 | 단계별 계산에서 같은 변수의 재할당이 더 명확할 때 |
| 메서드 매개변수 | `final` 채택 | 프로젝트 규칙이 시각적 간결성을 우선할 때 |
| 상속을 설계하지 않은 클래스 | `final` 채택 | 의도한 확장 지점이 있거나 프레임워크 프록시가 상속을 요구할 때 |
| 상속 가능한 클래스의 메서드 | 불변식을 지켜야 하면 `final` 채택 | 하위 타입별 재정의가 계약에 포함될 때 |
| 상수 | `static final` 채택 | 참조 대상이 가변 객체라면 별도 불변성 조치 필요 |

## 1. `final`이 보장하는 것

`final`은 적용 위치에 따라 다른 변경을 컴파일 단계에서 막는다.

- 변수와 필드: 초기화 이후 다른 값을 다시 대입하지 못한다.
- 매개변수: 메서드 본문에서 다른 값을 다시 대입하지 못한다.
- 메서드: 하위 클래스가 재정의하지 못한다.
- 클래스: 다른 클래스가 상속하지 못한다.

예를 들어 다음 필드는 생성 이후 다른 Repository로 교체할 수 없다.

```java
public final class ReservationService {
    private final ReservationRepository reservationRepository;

    public ReservationService(final ReservationRepository reservationRepository) {
        this.reservationRepository = reservationRepository;
    }
}
```

컴파일러가 막는 것은 참조의 재할당이다. Repository 객체 자체의 내부 상태나 외부 DB 상태까지 고정하지는 않는다.

## 2. 장점

### 2.1 변경 의도를 코드로 제한한다

주석이나 개발자 주의에만 의존하지 않고 컴파일러가 의도하지 않은 변경을 거부한다.

```java
final Reservation reservation = reservationRepository.findById(id);
reservation = anotherReservation; // 컴파일 오류
```

변수를 읽는 사람은 아래 코드를 더 확인하지 않아도 참조가 바뀌지 않는다는 사실을 알 수 있다. 긴 메서드나 여러 분기가 있는 코드에서 추적해야 할 상태가 줄어든다.

### 2.2 생성 이후 필드 구성을 안정적으로 유지한다

생성자 주입 필드에 `final`을 적용하면 객체가 생성될 때 필요한 의존성을 모두 받고, 이후 참조가 교체되지 않는 구조를 강제할 수 있다.

- 필드 누락을 생성 시점에 발견할 수 있다.
- 의존성 변경을 위한 Setter를 만들 이유가 줄어든다.
- 객체의 생명주기 동안 어떤 협력자를 사용하는지 명확해진다.

단, 의존 객체의 동작이나 상태가 변하지 않는다는 보장은 아니다.

### 2.3 상속과 재정의 범위를 명시한다

상속을 고려하지 않은 클래스에 `final`을 적용하면 우연한 하위 타입 생성을 막는다. 열린 상위 클래스의 특정 메서드에 `final`을 적용하면 하위 타입이 상위 타입의 불변식을 깨는 재정의를 막을 수 있다.

블랙잭 사례에서는 공통 상위 타입인 `Participant`만 확장 지점으로 열고, 구체 타입인 `Player`와 `Dealer`는 `final`로 제한했다.

- `Participant`: 의도한 상속 지점
- `Player`, `Dealer`: 더 확장할 이유가 없는 구체 타입

**판단: 상속은 기본 기능이 아니라 설계한 확장 지점에서만 허용한다.**

### 2.4 변경 가능성에 대한 검토를 강제한다

기존 `final`을 제거하려면 무엇을 바꾸려는지 코드 변경으로 드러난다. 재할당이나 상속이 정말 필요한지 리뷰할 지점이 생긴다.

이 장점은 확장을 영구히 금지하는 데 있지 않다. **확장을 묵시적으로 허용하지 않고 필요가 확인된 시점에 여는 데 있다.**

## 3. 단점과 제약

### 3.1 반복 사용에 따른 시각적 비용

모든 지역 변수와 매개변수에 `final`을 붙이면 선언이 길어진다.

```java
public ReservationResponse reserve(
        final Member member,
        final ReservationRequest request,
        final LocalDateTime requestedAt
) {
    // ...
}
```

매개변수가 많거나 제네릭 타입이 긴 코드에서는 핵심 타입과 이름을 읽는 데 방해가 될 수 있다. 이는 기능 문제가 아니라 팀 코드 스타일의 비용이다.

개인 기준에서는 재할당 방지 신호를 더 중요하게 보아 `final`을 사용한다. 팀 규칙이 반대라면 매개변수와 짧은 지역 변수까지 강제하지 않는다.

### 3.2 참조 불변성과 객체 불변성을 혼동할 수 있다

다음 코드는 `final`이어도 컬렉션을 변경할 수 있다.

```java
final List<String> names = new ArrayList<>();
names.add("kangrae"); // 허용
names.clear();        // 허용
```

객체 불변성이 필요하면 `final` 외에도 다음 조건을 확인해야 한다.

- 모든 상태 변경 경로 제거
- 생성 시 방어적 복사
- 가변 컬렉션을 외부에 직접 반환하지 않음
- 가변 하위 객체의 노출 방지
- 상속을 통한 상태 변경 방지

`final` 필드만 사용했다는 이유로 불변 객체라고 판단하지 않는다.

### 3.3 의도한 확장도 함께 막는다

클래스나 메서드를 `final`로 닫으면 새 하위 타입을 추가할 때 기존 코드를 수정해야 한다. 라이브러리처럼 사용자가 확장해야 하는 API에서는 명확한 확장 지점을 먼저 설계해야 한다.

다만 미래에 상속할 가능성만으로 클래스를 열어두지는 않는다. 실제 하위 타입 요구사항과 지켜야 할 계약이 확인됐을 때 연다.

### 3.4 프레임워크의 프록시 방식과 충돌할 수 있다

일부 프레임워크는 대상 클래스를 상속해 프록시를 만든다.

- Spring AOP가 클래스 기반 프록시를 사용하면 `final` 클래스는 상속할 수 없다.
- 클래스 기반 프록시에서는 `final` 메서드를 재정의해 가로챌 수 없다.
- `@Transactional`, `@Async`, `@Cacheable` 같은 기능은 실제 프록시 방식과 호출 경로를 확인해야 한다.
- JPA 지연 로딩은 공급자와 설정에 따라 엔티티 하위 프록시를 사용할 수 있다. 엔티티 클래스와 접근자를 `final`로 만들면 지연 로딩 방식이 제한될 수 있다.

따라서 Spring Bean과 JPA Entity에는 일반 클래스와 같은 기준을 기계적으로 적용하지 않는다.

**보류: 프레임워크가 관리하는 클래스의 `final` 적용은 현재 프록시·바이트코드 강화 설정을 확인한 뒤 결정한다.**

## 4. 적용 위치별 판단

### 4.1 필드

**채택: 생성 시 결정되고 생명주기 동안 교체하지 않는 필드는 `final`로 선언한다.**

대표 대상:

- 생성자로 주입받는 의존성
- 값 객체의 구성 값
- 생성 이후 동일한 참조를 유지할 컬렉션
- 객체의 식별자와 정책 객체

`final`을 사용하지 않을 조건:

- 상태 전이 자체가 다른 값의 대입으로 표현됨
- 프레임워크가 생성 이후 필드 값을 주입해야 함
- 캐시나 전략의 교체가 객체의 명시적 책임임

마지막 경우에도 단순 재할당보다 교체 메서드와 동시성 정책을 함께 설계한다.

### 4.2 지역 변수

**채택: 한 번 계산한 값을 다시 대입하지 않으면 `final`을 사용한다.**

지역 변수의 재할당이 필요하다면 먼저 값이 서로 다른 의미를 가지는지 확인한다.

```java
String status = "PENDING";
status = "CONFIRMED";
```

두 값이 서로 다른 단계나 상태를 뜻한다면 별도 변수, 작은 메서드, 도메인 상태 전이로 표현하는 편이 더 명확할 수 있다.

단, 누적 계산처럼 재할당이 알고리즘 자체를 직접 표현하는 경우에는 `final`을 억지로 유지하지 않는다.

### 4.3 매개변수

**채택: 메서드 입력값을 본문에서 다른 값으로 바꾸지 않도록 `final`을 사용한다.**

입력값을 정규화해야 한다면 같은 매개변수에 다시 대입하지 않고 새 이름을 사용한다.

```java
public Member create(final String name) {
    final String normalizedName = name.trim();
    return new Member(normalizedName);
}
```

원본 입력과 변환 결과의 의미가 분리된다. 반면 모든 매개변수에 붙이는 표기 비용은 존재하므로 협업 저장소에서는 팀 규칙을 우선한다.

### 4.4 클래스

**채택: 상속 계약을 설계하지 않은 구체 클래스는 `final`로 선언한다.**

다음 중 하나가 확인되면 열어둔다.

- 자연스러운 상위·하위 타입 관계가 있음
- 하위 타입이 지켜야 할 계약과 불변식이 정의됨
- 재정의 가능한 지점이 명확함
- 프레임워크가 클래스 상속 기반 프록시를 요구함

코드 재사용이나 테스트 대역 생성을 위해서만 상속을 열어두지는 않는다. 협력자 교체가 목적이라면 인터페이스와 조합을 우선한다.

### 4.5 메서드

**유지: 클래스 전체를 `final`로 닫을 수 있다면 개별 메서드에 중복 적용하지 않는다.**

상속 가능한 클래스에서만 다음 경우에 메서드 `final`을 사용한다.

- 알고리즘의 순서를 상위 타입이 보장해야 함
- 재정의하면 상위 타입의 불변식이 깨짐
- 확장 지점이 다른 메서드로 한정돼 있음

`private` 메서드는 하위 클래스가 재정의할 수 없으므로 `final`을 추가하지 않는다.

## 5. 사용하지 않을 이유

`final`을 사용하지 않으려면 다음 중 하나를 설명할 수 있어야 한다.

1. 재할당이 알고리즘이나 상태 전이를 더 정확하게 표현한다.
2. 상속과 재정의가 명시적으로 설계된 확장 계약이다.
3. Spring·JPA 등 프레임워크가 비-`final` 타입이나 메서드를 요구한다.
4. 팀 규칙이 매개변수와 짧은 지역 변수의 표기 비용을 더 크게 본다.

미래에 바뀔 수 있다는 이유만으로는 부족하다. 필요해지면 `final`을 제거할 수 있으며, 그 변경 자체가 판단을 다시 검토할 지점이 된다.

## 최종 판단 기준

> 재할당·재정의·상속의 필요성을 지금 설명할 수 없다면 `final`을 사용한다. 필드와 상속하지 않을 클래스에는 기본 적용하고, 지역 변수와 매개변수에도 재할당 방지를 위해 적용한다. 단, `final`은 참조와 확장 지점을 제한할 뿐 객체 불변성을 완성하지 않는다. Spring 프록시와 JPA 엔티티처럼 기술적으로 열려 있어야 하는 대상은 검증 후 예외로 둔다.

**최종 판단: 사용. 사용하지 않을 이유가 확인된 위치만 예외로 둔다.**

- [`Participant`와 구체 타입의 상속 범위 판단](abstract-class-vs-interface.md): `Player`와 `Dealer`를 `final`로 제한한 사례
- Java 컴파일러가 재할당, 메서드 재정의, 클래스 상속을 차단하는 언어 규칙

## 검증 범위

- 확인됨: 변수·필드 재할당, 메서드 재정의, 클래스 상속에 대한 컴파일 단계 제한
- 확인됨: 블랙잭 구체 타입의 의도하지 않은 추가 상속 제한 사례
- 확인 필요: 현재 프로젝트의 Spring 프록시 방식과 JPA 바이트코드 강화 설정
- 비범위: `final` 사용에 따른 JVM 성능 차이 측정
