# JPA 연관관계와 조회 계획

- 상태: `draft`
- 출처: Notion 기존 기록
- 주제: JPA 연관관계 방향, Fetch 전략, N+1 검증

## 결론

**채택: 필요한 탐색 방향만 단방향 연관관계로 표현한다.** 기본 FetchType만으로 조회 성능을 판단하지 않고, 유스케이스별 SQL을 확인한 뒤 조회 계획을 명시한다.

**유지: `Reservation → ReservationTime` 단방향 `ManyToOne`.** 예약 조회에는 시간이 필요하지만, 시간 조회에 예약 목록이 항상 필요한 것은 아니다.

## 빠른 기준

| 기준 | 판단 | 근거·예외 |
| --- | --- | --- |
| 양방향 연관관계 | 기본적으로 만들지 않음 | 양쪽 탐색이 실제 요구사항일 때만 추가 |
| 단방향 연관관계 | 우선 검토 | 필요한 탐색 방향만 표현 |
| 단방향 `OneToMany` | 기본 선택으로 두지 않음 | 외래 키 관리와 조회 비용을 함께 검토 |
| `OneToOne` | 기본 선택으로 두지 않음 | 라이프사이클과 접근 패턴이 완전히 같을 때만 검토 |
| 단방향 `ManyToOne` | 우선 검토 | 읽기 방향이 명확하고 외래 키 모델과 자연스럽게 맞음 |
| ID 참조 | 유효한 대안 | Aggregate 경계가 다르거나 결합을 낮춰야 할 때 검토 |
| 양방향 관계 + 엔티티 직접 사용 | 거부 | 탐색 범위, 상태 변경, 결합 범위를 동시에 넓힘 |

## 1. 엔티티 참조 방향

`Reservation → ReservationTime` 단방향 `ManyToOne`을 선택한다.

- 예약을 조회할 때 시간 정보가 필요하다.
- 시간을 조회할 때 예약 목록이 항상 필요한 것은 아니다.
- `ReservationTime`이 예약 컬렉션을 가지면 컬렉션 로딩 비용과 양방향 연관관계 동기화를 함께 관리해야 한다.
- 양방향 연관관계는 양쪽 탐색이 실제로 필요할 때만 추가한다.
- 연관관계는 편의가 아니라 실제 조회 방향을 근거로 설정한다.

### ID 참조 대안

참조 대신 `timeId`만 보관하는 구조도 선택지다.

- 장점: 조회가 명시적이고 엔티티 간 결합이 줄어든다.
- 단점: `reservation.getTime()` 탐색이 불가능하며, 필요한 곳에서 Repository를 통해 직접 조회해야 한다.
- 선택 기준: 자동 SQL을 신뢰하기 어렵다는 이유만으로 ID 참조를 선택하지 않는다. Aggregate 경계와 변경 가능성을 기준으로 판단한다.

> 필요한 탐색 방향만 연관관계로 표현하고, 미래에 사용할 가능성만으로 양방향 관계를 만들지 않는다.

## 2. `EAGER`의 정확한 의미

`EAGER`는 연관 엔티티가 함께 사용 가능한 상태로 로딩된다는 것만 보장한다.

- JOIN 한 번으로 가져오는 것은 보장하지 않는다.
- 추가 SELECT로 연관 엔티티를 가져올 수 있다.
- 같은 `EAGER` 설정이어도 단건 조회와 목록 조회의 SQL은 다를 수 있다.
- FetchType만 보고 성능을 판단하지 않고 실제 SQL을 확인한다.
- `@ManyToOne`과 `@OneToOne`의 JPA 기본 FetchType은 `EAGER`다. 의도한 지연 로딩이 필요하면 `LAZY`를 명시한다.

## 3. 관찰한 N+1

다음은 기존 기록에 남은 관찰 결과다. 현재 저장소에는 해당 SQL 로그와 재현 코드를 포함하지 않았으므로 **로컬 재검증 필요** 상태다.

예약 3개가 각각 Time과 Theme을 참조하는 목록 조회에서 다음 SQL을 확인했다.

- Reservation 목록 조회: 1회
- Time 조회: 3회
- Theme 조회: 3회
- 총 조회: 7회

**판단: `EAGER`만으로 효율적인 목록 조회를 보장하지 않는다.**

## 4. JOIN에 따른 행 증가

현재처럼 여러 `ManyToOne`을 조인하는 구조에서는 각 Reservation이 하나의 Time과 Theme만 가지므로, 루트 Reservation 행이 조합으로 증가하지 않는다.

반면 여러 `ToMany` 컬렉션을 동시에 조인하면 행이 곱집합처럼 증가할 수 있다.

```text
Reservation 1개
× Waitings 3개
× Payments 2개
= 결과 행 6개
```

따라서 "목록 조회는 행 폭증 때문에 항상 추가 SELECT를 사용한다"는 설명은 현재 구조의 근거가 될 수 없다.

- 확인한 사실: 단건과 목록 조회의 SQL이 달랐다.
- 확인하지 못한 내용: SQL 차이를 만든 정확한 JPA 내부 이유.

> 관찰한 SQL과 그 SQL이 만들어진 이유에 대한 추측을 구분해서 설명한다.

## 5. `EntityGraph`로 조회 계획 명시

`findAllByReserver`에 `EntityGraph`를 적용해 Time과 Theme을 조회 대상에 포함했다.

적용 전:

```text
Reservation 1회 + Time N회 + Theme N회
```

적용 후:

```sql
Reservation
LEFT JOIN Time
LEFT JOIN Theme
```

기존 기록에서는 총 7회 발생하던 SELECT가 JOIN이 포함된 SELECT 1회로 줄었다.

**판단: `EntityGraph`는 엔티티의 기본 FetchType을 변경하지 않고, 특정 조회에서 필요한 연관관계만 포함하는 조회 계획 도구다.**

## 6. 연관관계 추가 후 N+1 재검증

Reservation에 Member가 추가됐지만 기존 `EntityGraph`에 Member를 포함하지 않았다면, 목록 조회 계획을 다시 확인한다.

- Member가 `EAGER`면 추가 SELECT가 발생할 수 있다.
- Member가 `LAZY`면 접근 시점에 SELECT가 발생할 수 있다.
- 예약마다 다른 Member에 접근하면 N+1이 다시 발생할 수 있다.
- 영속성 컨텍스트와 배치 조회 설정에 따라 정확한 쿼리 수는 달라진다. 실제 SQL로 검증한다.

조회 목적별 선택지:

| 상황 | 선택지 | 제약 |
| --- | --- | --- |
| 연관 엔티티가 항상 필요한 엔티티 조회 | `EntityGraph` 또는 JPQL fetch join | 조회 메서드별 계획 관리 필요 |
| 화면에 필요한 필드만 조회 | DTO Projection | 엔티티 탐색·변경 용도로 재사용 불가 |
| 여러 컬렉션을 함께 조회 | 행 증가와 페이징을 우선 검토 | 단순 JOIN 확장은 중복 행과 성능 문제를 만들 수 있음 |
| 다수 프록시 초기화 | Batch Fetch 적용 | 전역 또는 관계별 설정의 영향 범위 확인 필요 |

## 7. Fetch 전략

**채택: 기본 연관관계는 `LAZY`로 두고, 조회 요구사항에 따라 필요한 연관관계만 명시적으로 로딩한다.**

- 항상 필요한 연관관계: `EntityGraph` 또는 fetch join
- 화면에 필요한 값만 조회: DTO Projection
- 여러 컬렉션 조회: 행 증가와 페이징 문제까지 검토
- 엔티티 변경: 기존 목록 조회 SQL을 다시 확인

> FetchType은 조회 성능을 완성하는 설정이 아니라 기본 로딩 시점을 정하는 설정이다. 실제 조회 계획은 유스케이스별로 설계한다.

## 8. JPA와 직접 SQL

JPA는 단순 CRUD와 조건 조회의 반복 구현을 줄인다.

- Spring Data JPA는 메서드 이름을 분석해 쿼리를 생성할 수 있다.
- 객체와 연관관계를 중심으로 저장과 조회를 표현할 수 있다.
- 생성 SQL을 직접 지정하지 않으면 비효율적 조회를 늦게 발견할 수 있다.

따라서 JPA 자동화를 포기하는 것이 기준은 아니다.

1. 연관관계를 도메인에 맞게 설계한다.
2. 실제 SQL을 관찰한다.
3. 문제가 있는 조회만 `EntityGraph`, fetch join, Projection 등으로 명시한다.
4. 그래도 결합 비용이 크다면 ID 참조 구조를 검토한다.

## 최종 판단 기준

> 엔티티 연관관계는 필요한 탐색 방향과 Aggregate 경계를 기준으로 설정한다. 기본 로딩 전략만 믿지 않고 실제 SQL을 관찰하며, 조회별로 필요한 연관관계를 명시한다. 확인한 사실과 동작 원인에 대한 추측은 구분해서 설명한다.
