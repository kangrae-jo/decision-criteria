# 비동기 메시지 전달 방식 선택

- 상태: `adopted`
- 주제: 동기 호출, 일시적 알림, 작업 큐, 이벤트 스트림
- 선택: 요구사항 조합으로 전달 모델 결정

## 결론

**채택: 호출 결과가 즉시 필요하고 같은 요청에서 성공 여부를 확정해야 하면 동기 호출을 사용한다.** 비동기 처리가 필요하다는 근거가 없으면 브로커를 도입하지 않는다.

**채택: 최신 상태를 다시 조회할 수 있고 알림 누락을 허용하면 일시적 알림을 사용한다.**

**채택: 하나의 작업을 여러 작업자 중 한 명이 처리하고 완료 이후 재생이 필요 없으면 작업 큐를 사용한다.**

**채택: 발생한 사실을 보존하고 여러 소비자 그룹이 독립적으로 처리하거나 재처리해야 하면 이벤트 스트림을 사용한다.**

## 빠른 기준

| 질문 | 판단 |
| --- | --- |
| 호출자가 즉시 결과를 받아야 하는가? | 동기 호출 |
| 누락돼도 최신 상태 재조회로 복구할 수 있는가? | 일시적 알림 |
| 여러 작업자 중 한 명만 처리해야 하는가? | 작업 큐 |
| 여러 소비자 그룹이 같은 기록을 각각 처리해야 하는가? | 이벤트 스트림 |
| 장애 이후 특정 시점부터 다시 처리해야 하는가? | 보존형 이벤트 스트림 |
| 이벤트가 현재 상태를 복원하는 원본인가? | Event Sourcing 별도 검토 |

질문 하나만으로 선택하지 않는다. 데이터의 의미가 이벤트여도 보존과 재처리가 필요 없다면 작업 큐나 일시적 알림으로 충분할 수 있다.

## 1. 동기 호출

다음 조건이면 동기 호출을 유지한다.

- 호출자가 결과를 받아 다음 행동을 결정해야 한다.
- 실패를 현재 요청의 실패로 반환해야 한다.
- 처리량 분산이나 장애 격리가 아직 필요하지 않다.

비동기화하면 응답 지연은 줄일 수 있지만 처리 완료 확인, 재시도, 중복 방지, 상태 조회가 새로 필요하다.

## 2. 일시적 알림

알림은 상태 자체가 아니라 변경 사실만 전달한다.

- 최신 상태의 원본이 별도로 존재한다.
- 연결 복구 후 재조회할 수 있다.
- 알림 일부가 유실돼도 데이터 자체는 잃지 않는다.
- 과거 알림 재생과 소비자별 처리 위치가 필요하지 않다.

누락 없는 처리가 요구되면 일시적 알림을 사용하지 않는다.

## 3. 작업 큐

작업 큐는 처리해야 할 명령을 작업자에게 분배한다.

- 같은 작업을 여러 작업자 중 하나가 처리한다.
- 성공한 작업은 다시 읽을 필요가 없다.
- ACK, 재시도, 실패 격리가 중요하다.
- 소비자는 중복 전달을 견딜 수 있어야 한다.

작업 이력을 장기간 보존하거나 신규 소비자가 과거 작업을 다시 읽어야 한다면 이벤트 스트림을 검토한다.

## 4. 이벤트 스트림

이벤트 스트림은 소비 여부와 별개로 기록을 보존한다.

- 여러 소비자 그룹이 같은 이벤트를 독립적으로 처리한다.
- 장애 복구나 신규 소비자를 위해 과거 이벤트를 재생한다.
- Aggregate나 partition 단위 순서가 필요하다.
- 보존 기간과 용량을 운영 정책으로 관리할 수 있다.

이벤트 스트림을 사용한다고 이벤트가 자동으로 시스템의 원본이 되지는 않는다. 원본 데이터의 위치는 별도로 결정한다.

## 5. 선택 순서

1. 동기 호출로 해결할 수 있는지 확인한다.
2. 비동기가 필요하면 누락 허용 여부를 확인한다.
3. 누락을 허용하지 않으면 하나의 작업 처리인지 여러 독립 소비인지 구분한다.
4. 재처리 기간과 순서 보장 범위를 결정한다.
5. 전달 모델이 결정된 뒤 제품을 선택한다.

## 트레이드오프

| 방식 | 얻는 것 | 부담하는 것 |
| --- | --- | --- |
| 동기 호출 | 단순한 성공·실패와 흐름 | 호출자와 처리자의 시간적 결합 |
| 일시적 알림 | 작은 구현과 낮은 저장 비용 | 연결 단절 중 누락 |
| 작업 큐 | 작업 분산, ACK, 재시도 | 처리 이력과 재생 능력 제한 |
| 이벤트 스트림 | 보존, 재처리, 독립 소비자 | 저장 용량, offset, 순서와 중복 처리 |

## 비범위

- Kafka, RabbitMQ, Redis 중 제품 선택
- DB 변경과 이벤트 발행의 원자성
- Event Sourcing의 데이터 모델

## 검증 방법

- 소비자가 중단된 동안 발생한 데이터를 복구해야 하는지 확인한다.
- 같은 데이터를 처리하는 독립 소비자 그룹 수를 기록한다.
- 허용 가능한 누락, 중복, 순서 변경 범위를 명시한다.
- 필요한 재처리 기간과 예상 데이터량을 계산한다.
- 브로커 장애 시 사용자 요청의 성공 기준을 정의한다.

## 최종 판단 기준

> 즉시 결과와 같은 요청의 성공 확정이 필요하면 동기 호출을 유지한다. 최신 상태 재조회로 누락을 복구할 수 있으면 일시적 알림을, 하나의 작업을 한 작업자가 처리하면 작업 큐를, 기록 보존과 독립 소비자별 재처리가 필요하면 이벤트 스트림을 선택한다. 전달 모델을 결정한 뒤 제품을 선택한다.
