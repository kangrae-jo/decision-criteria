# 추상 클래스와 인터페이스 선택

- 상태: `validated`
- 출처: 우아한테크코스 블랙잭·장기 미션과 코드 리뷰
- 주제: 상속, 행위 계약, 상태와 불변식, 조합

## 결론

**채택: 먼저 자연스러운 상위 타입 관계인지 확인한다.** 그 관계가 성립한 뒤 공통 상태와 불변식까지 공유하면 추상 클래스를, 교체 가능한 행위 계약만 필요하면 인터페이스를 우선 검토한다.

**거부: 코드 중복 제거만을 목적으로 상속하지 않는다.** 상위 타입 관계가 부자연스럽다면 조합으로 공통 기능을 분리한다.

## 빠른 기준

| 질문 | 판단 |
| --- | --- |
| 하위 타입을 상위 타입으로 자연스럽게 설명할 수 있는가? | 성립하지 않으면 상속 거부 |
| 공통 상태와 생성 규칙, 불변식을 함께 관리해야 하는가? | 추상 클래스 우선 검토 |
| 구현체마다 교체할 행위 계약만 필요한가? | 인터페이스 우선 검토 |
| 목적이 구현 코드 재사용뿐인가? | 조합 우선 검토 |
| 하위 클래스의 추가 확장을 허용할 이유가 있는가? | 없다면 구체 클래스를 `final`로 제한 |
| 행위가 상태와 독립적으로 바뀔 가능성이 있는가? | 인터페이스를 구현한 전략 객체로 분리 |

## 1. 판단 순서

추상 클래스와 인터페이스를 선택하기 전에 상속 관계 자체가 필요한지 확인한다.

1. “하위 타입은 상위 타입이다”라는 문장이 도메인에서 자연스러운지 확인한다.
2. 공통 상태와 불변식을 하나의 상위 타입이 책임져야 하는지 확인한다.
3. 구현체별 차이가 교체 가능한 행위인지 확인한다.
4. 공통 구현을 재사용하는 것만 목적이라면 조합으로 해결할 수 있는지 확인한다.

상태와 행위의 구분은 두 번째 판단 기준이다. **첫 번째 기준은 타입 관계의 타당성이다.**

## 2. 인터페이스를 선택한 사례: 장기

장기에서는 기물을 구분하는 핵심 차이를 이동 행위로 판단해 `MoveStrategy` 인터페이스를 선택했다.

- 기물마다 이동 규칙이 다르다.
- 이동 전략 자체에 기물별 가변 상태가 필요하지 않았다.
- `Piece`는 구체 이동 구현이 아니라 `MoveStrategy` 계약에 의존할 수 있다.
- 동일한 이동 전략을 여러 기물이 공유할 수 있다.

리뷰 과정에서는 `MoveStrategy`가 `PieceType`까지 가지면 기물의 정체성과 이동 행위가 결합된다는 문제가 드러났다. 이에 `Piece`가 `PieceType`을 가지고, 타입이 이동 전략을 제공하는 방향을 검토했다.

**판단: 인터페이스는 교체 가능한 행위에 집중한다. 행위 주체의 정체성이나 상태까지 전략에 넣지 않는다.**

### 제약

- 전략마다 공통 상태가 생기면 별도 상태 객체 또는 추상 클래스가 필요한지 다시 검토해야 한다.
- 타입과 전략이 항상 일대일이라고 가정하면 같은 전략을 공유하는 타입을 중복 구현할 수 있다.
- 인터페이스를 사용했다는 사실만으로 결합이 낮아지지는 않는다. 전략의 책임 범위가 명확해야 한다.

## 3. 추상 클래스를 선택한 사례: 블랙잭

블랙잭에서는 Player와 Dealer의 공통 상위 개념으로 `Participant` 추상 클래스를 선택했다.

- Player와 Dealer는 카드와 이름 같은 상태를 공유한다.
- 카드 추가, 점수 계산 등 공통 행위를 가진다.
- 공통 상태에 적용되는 생성 규칙과 불변식을 한곳에서 관리할 수 있다.
- 카드 추가 가능 여부인 `canDraw()`만 하위 타입별로 다르게 구현한다.
- `Player`와 `Dealer`를 `final`로 선언해 의도하지 않은 추가 상속을 제한한다.

“Player와 Dealer는 게임 Participant다”라는 타입 관계는 자연스럽다. 공통 상태와 행위도 존재하므로 이 사례에서는 추상 클래스가 적절하다.

### 제약

- Java 클래스 상속은 하나만 가능하므로 다른 상위 구현을 상속할 수 없다.
- 하위 타입은 상위 클래스의 생성자와 상태 표현에 결합된다.
- `final`은 추가 상속을 막지만 상위 클래스와 하위 클래스 사이의 결합을 제거하지 않는다.
- `canDraw()` 규칙이 독립적으로 교체되거나 조합돼야 한다면 `DrawPolicy` 같은 전략 인터페이스로 분리하는 편이 낫다.

## 4. 거부한 사례: `Dealer extends Player`

초기 구현에서는 Dealer가 Player를 상속했다. 두 타입이 유사한 상태와 행위를 가진다는 이유였다.

리뷰에서는 다음 문제가 제기됐다.

- “Dealer는 Player인가?”라는 타입 관계가 자연스럽지 않다.
- 타입 구분만을 위해 상속할 필요가 없다.
- 공통 메서드를 가진 객체를 필드로 두는 조합도 가능하다.
- Dealer가 Player의 동작을 재정의하지 않는다면 별도 하위 타입이 필요한지도 확인해야 한다.

이를 통해 Player와 Dealer의 공통 상위 개념인 `Participant`를 찾았다.

**판단: 공통 코드가 보이더라도 바로 상속하지 않는다. 도메인에서 자연스러운 공통 상위 개념을 먼저 찾는다. 찾을 수 없다면 조합을 선택한다.**

## 5. 추상 클래스와 인터페이스를 함께 사용하는 경우

두 방식은 항상 대체 관계가 아니다.

예를 들어 Participant가 카드와 이름의 불변식을 관리하고, 카드 뽑기 규칙이 독립적으로 변한다면 다음 구조를 사용할 수 있다.

```text
Participant 추상 클래스
└── DrawPolicy 인터페이스를 필드로 보유
    ├── PlayerDrawPolicy
    └── DealerDrawPolicy
```

- 장점: 공통 상태와 행위 변경을 분리할 수 있다.
- 비용: 타입과 객체 수가 늘고 현재 요구사항보다 복잡한 구조가 될 수 있다.
- 적용 조건: 뽑기 규칙이 독립적으로 교체·조합되거나 구현 수가 증가할 때만 도입한다.

현재 블랙잭 사례에서는 `canDraw()` 추상 메서드만으로 차이를 표현할 수 있으므로 별도 전략 분리는 **보류**한다.

## 최종 판단 기준

> 먼저 자연스러운 상위 타입 관계인지 확인한다. 공통 상태와 불변식까지 공유하면 추상 클래스를, 교체 가능한 행위 계약만 필요하면 인터페이스를 우선 검토한다. 코드 재사용만 목적이거나 타입 관계가 부자연스럽다면 상속을 거부하고 조합을 선택한다.
