# 트래픽 폭주 시 요청 수용·대기·거절

- 상태: `adopted`
- 검토일: 2026-10-14
- 주제: 과부하 제어, Admission Control, 제한된 대기, Load Shedding, 429, 503, 가상 대기열
- 선택: 처리 한도와 대기 시간을 제한하고, 병목 앞에서 조기에 수용하거나 거절

## 결론

**채택: 지속 가능한 처리량을 넘는 요청은 병목 자원을 점유하기 전에 제한한다.** 수용한 요청의 동시 실행 수와 대기열에는 상한과 시간제한을 둔다.

**채택: 짧은 순간 부하만 제한된 큐로 흡수한다.** 큐 크기는 동시 사용자 수가 아니라 서비스가 목표 응답 시간 안에 처리할 수 있는 양으로 정한다.

**거부: 대기열이 가득 차면 Spring이 자동으로 `429 Too Many Requests`를 반환한다고 가정한다.** HTTP 계층에 도달하기 전에는 연결 거절이나 타임아웃으로 끝날 수 있으며, HTTP 응답 코드는 제한을 수행하는 구성 요소가 명시적으로 반환해야 한다.

**보류: 연결 수, 스레드 수, DB 커넥션 수와 큐 크기의 구체적인 값은 측정 전에는 확정하지 않는다.**

## 빠른 기준

| 상황 | 판단 |
| --- | --- |
| 특정 사용자·클라이언트·테넌트가 허용 빈도를 초과함 | `429`와 재시도 조건 반환 |
| 서비스 전체가 일시적으로 처리 능력을 초과함 | `503` 우선 검토 |
| HTTP 요청을 해석하기 전에 용량이 소진됨 | 연결 거절·리셋·타임아웃까지 클라이언트 실패 처리에 포함 |
| 짧은 폭주를 허용 대기 시간 안에 해소할 수 있음 | 상한이 있는 대기열 사용 |
| 대기 시간이 처리 시간 예산을 넘음 | 조기에 거절하여 자원 회수 |
| 결과를 현재 요청에서 기다릴 필요가 없음 | 작업을 내구적으로 수용하고 `202 Accepted` 같은 비동기 흐름 검토 |
| 사용 순서·입장 인원·공정성을 보장해야 함 | 서버가 입장권을 관리하는 가상 대기열 검토 |
| 잠시 후 다시 시도하도록 안내하면 충분함 | 재시도 화면과 제한된 backoff 사용 |

## 1. 부하와 제한 대상을 구분

“수십만 명이 동시에 접속한다”만으로 서버 설정을 정하지 않는다. 다음 값을 분리한다.

- 동시 사용자 수: 서비스를 사용 중인 사람 수
- 요청 도착률: 초당 들어오는 요청 수
- 동시 처리 수: 아직 완료되지 않은 요청 수
- 처리 시간: 요청 하나가 자원을 점유하는 시간
- 폭주 지속 시간: 평상시 처리량을 넘는 시간이 얼마나 이어지는지

같은 사용자 수라도 요청 빈도와 처리 시간이 다르면 필요한 용량이 달라진다. 먼저 대표 API가 목표 응답 시간을 지키며 지속할 수 있는 처리량을 측정한다.

## 2. 모든 대기 지점을 하나의 큐로 보지 않음

Spring MVC와 내장 Tomcat을 사용해도 요청은 여러 지점에서 별도로 대기할 수 있다.

| 지점 | 제한 대상 | 포화 시 가능한 결과 |
| --- | --- | --- |
| CDN·Gateway·Load Balancer | 요청 빈도와 동시 유입 | 명시적인 `429`·`503`, 연결 종료 |
| OS·Tomcat Connector | 연결 수와 accept backlog | 연결 거절 또는 타임아웃 |
| 요청 Executor | 실행 중인 작업과 작업 대기 | 지연 증가, 거절 정책에 따른 실패 |
| DB 커넥션 풀 | DB 동시 작업과 연결 대기 | 대기 후 커넥션 획득 실패 |
| 외부 API 클라이언트 | 외부 호출 동시 수와 응답 대기 | 타임아웃, 재시도에 따른 부하 증폭 |

Tomcat의 `maxConnections`와 `acceptCount`는 같은 값이 아니다. Connector의 연결 한도를 넘으면 OS가 추가 연결을 대기시키고, 그 큐까지 차면 연결이 거절되거나 타임아웃될 수 있다. 따라서 애플리케이션 코드가 모든 초과 요청에 HTTP 응답을 보낼 수 있다고 가정하지 않는다.

Tomcat의 `connectionTimeout`도 API 전체 처리 시간제한이 아니다. 연결 수락 후 요청 URI를 기다리는 시간 등의 Connector 설정과, 애플리케이션의 전체 처리 시간 예산을 구분한다.

가상 스레드와 Executor 구현은 스레드 관련 한도의 의미를 바꿀 수 있지만 DB, 외부 API와 CPU의 처리 한도를 없애지는 않는다. 실제 Spring Boot·Tomcat 버전과 실행 구성은 **확인 필요**다.

## 3. 수용·대기·거절 위치

**채택: 보호할 병목보다 앞에 있고, 정책 판단에 필요한 정보를 가진 가장 저렴한 계층에서 요청을 제한한다.**

- 전체 유입과 사용자별 빈도 제한은 Gateway 같은 앞단에서 우선 처리한다.
- API별 비용과 업무 우선순위가 필요하면 애플리케이션 수준의 동시 실행 제한을 추가한다.
- DB 커넥션 풀이 먼저 포화된다면 Tomcat 큐만 늘리지 않고 DB로 향하는 동시 작업 수를 제한한다.
- 조회와 결제처럼 비용과 중요도가 다른 요청은 하나의 전역 한도로만 묶지 않는다.

큐는 처리 능력을 늘리지 않는다. 순간 부하를 평탄화할 뿐이며, 지속 유입량이 처리량보다 크면 대기 시간만 계속 증가한다. 오래된 요청의 가치가 사라지는 서비스에서는 큰 큐보다 빠른 거절이 낫다.

## 4. `429`, `503`, 무응답을 구분

| 결과 | 의미 | 클라이언트 처리 |
| --- | --- | --- |
| `429 Too Many Requests` | 정의한 주체나 범위가 요청 빈도 정책을 초과함 | `Retry-After`가 있으면 따르고 제한된 재시도 |
| `503 Service Unavailable` | 서비스가 일시적인 과부하나 점검으로 처리할 수 없음 | 재시도 가능 여부와 시간을 확인 |
| 연결 거절·리셋·타임아웃 | HTTP 응답 전에 연결 또는 상위 계층에서 실패함 | 네트워크 실패로 분류하고 무제한 즉시 재시도 금지 |

`429`와 `503`에는 가능하면 기계가 해석할 수 있는 오류 코드와 `Retry-After`를 제공한다. 다만 복구 시간을 예측할 수 없으면 임의의 값을 보내지 않는다.

재시도는 횟수와 전체 시간을 제한하고 지수 backoff와 jitter를 적용한다. 변경 요청은 멱등하거나 멱등 키가 있을 때만 자동 재시도한다. 그렇지 않으면 과부하가 재시도 폭주와 중복 처리로 확대될 수 있다.

## 5. 재시도 화면과 가상 대기열

`429`를 받은 클라이언트가 안내 화면을 보여주는 것만으로는 대기열이 만들어지지 않는다.

| 구분 | 재시도 화면 | 가상 대기열 |
| --- | --- | --- |
| 서버 상태 | 요청을 거절하고 다음 시도 시점만 안내 | 순서와 입장 가능 여부를 서버가 보관 |
| 공정성 | 보장하지 않음 | 입장 정책에 따라 보장 가능 |
| 원 서버 보호 | 재시도 빈도에 의존 | 입장권을 가진 요청만 원 서버로 전달 |
| 추가 책임 | backoff와 오류 안내 | 입장권 만료, 중복 접속, 우회 방지, 다중 인스턴스 상태 관리 |

**채택: 단순 과부하 안내가 목적이면 재시도 화면을 사용한다.** 사용 순서나 제한된 인원만 입장시키는 것이 요구사항이면 별도의 가상 대기열을 설계한다. 클라이언트의 반복 요청만으로 순서를 정하지 않는다.

## 6. 대기 한도 결정

대기열의 초깃값은 다음 순서로 정한다.

1. 대표 API의 지속 가능한 처리량과 병목을 측정한다.
2. 사용자가 허용할 최대 응답 시간에서 실제 처리 시간을 뺀 대기 예산을 정한다.
3. 그 시간 안에 비울 수 있는 요청 수보다 큐가 커지지 않게 상한을 둔다.
4. 초과 요청은 앞단에서 거절하고, 실제 폭주 시험으로 회복 시간을 확인한다.

각 계층의 타임아웃은 하나의 전체 시간 예산으로 연결한다. 상위 요청 종료가 하위 DB 쿼리나 외부 호출의 취소로 전파되는지 확인하고, 하위 타임아웃은 호출자의 남은 시간보다 짧게 둔다.

서버 증설도 자동 해결책으로 두지 않는다. 애플리케이션 인스턴스를 늘리면 전체 DB 커넥션과 외부 API 동시 호출이 함께 증가하므로 공유 병목의 전역 한도를 확인한다.

## 비용·제약

- 작은 큐와 빠른 거절은 지연과 장애 확산을 줄이지만 순간 요청의 성공률을 낮출 수 있다.
- 큰 큐는 짧은 폭주를 흡수하지만 메모리 사용, 꼬리 지연과 만료된 작업 처리를 늘린다.
- 앞단 제한은 애플리케이션을 보호하지만 업무별 비용과 사용자 상태를 충분히 모를 수 있다.
- 애플리케이션 제한은 세밀한 정책을 적용할 수 있지만 이미 요청 처리 자원을 일부 사용한다.
- 가상 대기열은 공정성을 제공할 수 있지만 별도의 고가용성 상태와 운영 체계가 필요하다.

## 검증 방법

- 대표 API에 단계 부하와 순간 폭주를 가해 지속 처리량과 포화 지점을 구한다.
- 수용 RPS, 거절 RPS, 동시 처리 수, 큐 길이와 가장 오래된 대기 시간을 함께 기록한다.
- p95·p99 응답 시간, CPU·메모리·GC, 요청 Executor, DB 커넥션 대기와 외부 API 지연을 함께 본다.
- 오류를 `429`, `503`, 연결 실패, 타임아웃과 애플리케이션 오류로 나눠 기록한다.
- 클라이언트 재시도로 유입량이 얼마나 증폭되는지 확인한다.
- 부하 제거 후 큐가 비워지고 정상 응답 시간으로 회복되는 시간을 측정한다.
- 가상 대기열을 사용하면 순서, 입장권 만료, 새로고침·재접속과 우회 요청을 검증한다.

부하 생성기 자체가 먼저 포화되지 않는지는 [부하 테스트 생성기 선택](load-test-generator-selection.md)의 기준으로 확인한다.

## 최종 판단 기준

> 동시 사용자 수만으로 큐를 정하지 않는다. 지속 가능한 처리량과 전체 시간 예산을 기준으로 실행 수와 대기열을 제한하고, 공유 병목보다 앞에서 초과 요청을 조기에 거절한다. 요청 빈도 제한은 `429`, 서비스 전체의 일시적 과부하는 `503`, HTTP 이전 실패는 연결 오류로 구분한다. 공정한 순서와 입장 제어가 요구될 때만 별도의 가상 대기열을 도입한다.
