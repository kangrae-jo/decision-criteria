# SSE를 통한 목록 변경 알림

- 상태: `validated`
- 출처: 배송 요청 목록 자동 갱신 조사·승인·구현 기록과 작성자의 직접 실행 확인
- 구현 근거: [2026-setty PR #247](https://github.com/woowacourse-teams/2026-setty/pull/247)
- 요구사항: [2026-setty 이슈 #244](https://github.com/woowacourse-teams/2026-setty/issues/244)
- 조사 기준: `develop`의 `1de1f20` (제공된 조사 기록)
- 주제: SSE, Polling, WebSocket, REST, 트랜잭션과 외부 알림

## 결론

**채택: 기존 REST API를 유지하고, SSE로 목록 변경 사실만 알린다.** 현재 요구는 서버에서 기사 앱으로 전달하는 단방향 알림이다. 앱은 알림을 받으면 기존 GET으로 최신 목록을 다시 조회한다.

**보류: WebSocket 도입.** 현재는 요청 수락을 기존 POST로 처리할 수 있으므로 지속적인 양방향 연결을 추가할 근거가 부족하다.

**유지: 단일 서버와 기존 주문·배송 상태 동기화.** 앱에 보내는 외부 알림만 저장 성공 이후로 분리한다.

## 빠른 기준

| 방식 | 얻는 것 | 감수할 비용·제약 | 내 판단 |
| --- | --- | --- | --- |
| SSE | 서버의 변경을 단방향으로 전달 | 장기 연결, 인증, 재연결, 누락 복구 관리 | 목록 변경 알림에 채택 |
| 주기적 Polling | 기존 GET 재사용, 단순한 구현과 장애 추적 | 변경이 없어도 조회 반복, 주기와 반영 지연의 절충 | 단기·장애 보조안으로 채택. 상시 적용과 주기는 보류 |
| WebSocket | 지속적인 양방향 통신과 바이너리 메시지 지원 | 연결·인증·메시지 규약·복구 설계 추가 | 양방향 요구가 확정될 때까지 보류 |

## 1. 해결하려던 문제

처음에는 HTTP 통신을 Polling으로 보았지만, 제공된 조사 기록에서는 주기적 Polling이 없었다.

- `useRequests.ts`: 최초 목록 조회
- `RequestListScreen.tsx`: 화면 복귀, 수동 새로고침, 수락 성공 시 재조회
- `JdbcDeliveryQueryRepository.java`: `REQUESTED`이면서 미배정인 배송 요청 조회

문제는 **화면을 계속 보고 있는 동안 신규 요청과 다른 기사의 수락이 자동 반영되지 않는 것**이었다. Polling 부하가 높다는 관측 결과는 없었다.

HTTP를 사용한다는 사실만으로 Polling은 아니다. SSE도 HTTP 기반이다. 이 선택은 HTTP를 버리는 결정이 아니라 목록 변경을 감지하는 방식을 추가하는 결정이다.

## 2. 내가 SSE를 선택한 이유

1. 필요한 실시간 통신 방향이 서버에서 앱으로 한정된다.
2. 배송 요청 조회와 수락은 기존 GET·POST로 처리할 수 있다.
3. 목록 변경 사실만 받으면 기존 조회 로직을 재사용할 수 있다.
4. 현재 Spring MVC 구성을 유지하면서 `SseEmitter`를 활용할 수 있다.

**거부: 실시간 기능이라는 이유만으로 WebSocket이나 WebFlux를 도입하지 않는다.** 실제 요구에 없는 통신 기능이나 실행 모델을 먼저 추가하지 않는다.

다만 SSE도 연결 관리 비용이 있다. WebSocket이 항상 더 복잡하거나 SSE가 항상 더 저렴하다는 일반론을 선택 근거로 삼지는 않는다.

실시간 위치 교환이나 채팅처럼 빈번한 양방향 통신이 확정되면 WebSocket을 재검토한다. WebSocket에 STOMP나 메시지 브로커가 반드시 필요한 것은 아니다.

## 3. 변경 알림과 상태 조회를 분리한다

채택한 흐름은 다음과 같다.

배송 요청 생성·수락 → DB 커밋 → SSE 변경 알림 → 기존 GET 재조회 → 목록 갱신

- 유지: GET은 최신 목록 조회, POST는 수락·상태 변경을 담당한다.
- 채택: SSE는 “목록이 바뀌었으니 다시 조회하라”는 작은 신호만 전달한다.
- 채택: 신규 요청 추가와 다른 기사의 수락을 모두 알림 대상으로 삼는다.
- 거부: 내부 주문 이벤트를 그대로 앱에 전송하지 않는다. 기록상 `OrderRequested.java`의 주소·전화번호는 목록 갱신 알림에 불필요하다.

기존 조회와 화면 처리 경로를 재사용하면 정렬과 로컬 거절 필터를 유지하기 쉽다. 이벤트마다 클라이언트가 목록 상태를 직접 조립하는 책임도 줄어든다.

대신 알림을 받은 앱들이 GET을 다시 호출한다. 변경이 잦으면 조회가 몰릴 수 있으므로 연속 알림 병합과 중복 조회 방지가 필요하다. **SSE를 사용한다는 사실만으로 GET·DB 부하 감소가 보장되지는 않는다.**

## 4. 저장 성공과 알림 전송의 경계를 나눈다

**채택: DB 커밋이 성공한 뒤 앱에 알리고, 알림 실패가 이미 성공한 저장을 실패로 바꾸지 않게 한다.**

커밋 전에 알리면 앱이 아직 저장되지 않은 목록을 조회하거나, 이후 롤백될 변경을 먼저 전달받을 수 있다.

- 유지: 주문·배송의 기존 트랜잭션과 상태 동기화
- 채택: 외부 앱 알림에 한정한 커밋 이후 전달 경계
- 거부: 앱 알림을 이유로 기존 도메인 동기화까지 비동기로 변경

제공 기록에서는 배송 영역의 `AFTER_COMMIT`·`@Async` 금지 규칙에 대해 외부 앱 알림만 예외로 승인했다. 이 예외를 다른 도메인 처리로 확대하지 않는다.

커밋 이후 실행과 비동기 실행은 별개다. 커밋 이후로 옮겼다는 이유만으로 느린 클라이언트의 전송 대기가 격리되지는 않는다. 전송 자원과 대기열 제한도 확인해야 한다.

또한 DB 커밋과 SSE 전달은 하나의 원자적 작업이 아니다. 저장 성공 후 알림이 누락될 수 있음을 전제로 복구 경로를 둔다.

## 5. 재연결과 재조회를 선택에 포함한다

**채택: 연결 복구와 앱 복귀 시 기존 GET으로 최신 상태를 다시 맞춘다.** SSE 연결 자체를 이벤트 누락 없는 전달 보장으로 보지 않는다.

- 연결 준비 후 최초 목록을 조회한다.
- 조회 중 변경 알림을 받으면 현재 조회가 끝난 뒤 다시 조회한다.
- 겹친 조회의 오래된 응답이 최신 목록을 덮어쓰지 않게 조정한다.
- 백그라운드 진입 시 연결을 닫고, 포그라운드 복귀 시 재연결·재조회한다.
- Bearer 인증은 유지하되 토큰을 URL에 넣지 않는다. 로그아웃·토큰 변경 시 연결 수명도 관리한다.

`Last-Event-ID`는 마지막 이벤트 ID를 전달하는 수단이지 서버의 이벤트 저장·재전송을 자동 제공하는 기능이 아니다. 또한 스트리밍 수신을 직접 구현한다면 파싱과 재연결도 별도로 처리해야 한다.

보조 Polling은 장애나 누락을 보정하는 선택지로 남긴다. 기록의 “60초마다 재조회”는 제안값이며 확정한 운영 주기나 구현 결과가 아니다. 재연결 시 재조회만으로 같은 연결에서 조용히 누락된 알림까지 즉시 복구되지는 않는다.

모든 이벤트의 영구 보존과 재전송이 요구된다면 SSE 선택과 별개로 저장·전달 보장 설계를 다시 검토한다.

## 6. 현재 규모와 수정 범위를 유지한다

- **유지: 단일 서버.** 초기 연결은 서버 메모리에서 관리하고, 여러 인스턴스 간 알림 공유는 이번 범위에서 제외한다.
- **유지: Spring MVC.** SSE 때문에 WebFlux로 전환하지 않는다.
- **채택: 앱의 별도 스트림 수신 계층.** 기록상 기존 `http.ts`는 전체 응답을 `res.text()`로 받은 뒤 JSON으로 파싱하므로 SSE 수신에 그대로 사용하지 않는다.
- **유지: 구현 변경 범위는 서버의 `delivery`와 `apps`.** 범위를 넓혀야 한다면 별도로 보고하고 결정한다.
- **비범위: 백그라운드·앱 종료 상태의 배송 알림.** SSE는 모바일 OS의 실행 제한을 해결하지 않는다. 푸시 알림은 별도 판단이다.

장기 연결에는 heartbeat, 끊어진 연결 정리, 전송 대기열 제한, 프록시 버퍼링·타임아웃 검증이 필요하다. 다중 서버로 확장하면 다른 서버에 연결된 앱에도 변경을 전달할 방법을 추가해야 한다.

**거부: 목록 최신화가 중복 수락 방지까지 해결한다고 보지 않는다.** 동시 수락에서 성공을 한 건으로 제한하는 책임은 서버의 트랜잭션·잠금·조건부 갱신 등에 남는다.

## 최종 판단 기준

> 나는 서버에서 앱으로 목록 변경만 알려야 하고 기존 API로 최신 상태를 복구할 수 있다면, REST를 유지하고 SSE를 추가한다. 알림은 저장 성공 이후의 작은 변경 신호로 제한하고 재연결 시 재조회한다. 현재 필요 없는 양방향 통신과 다중 서버 구조는 먼저 도입하지 않는다. 연결 유지 비용과 알림 누락 가능성은 감수하되, 전달 보장과 성능 개선은 별도로 검증한다.

- 확인됨: 제공 기록에 명시된 선택과 승인 내용, `2026-setty`의 이슈 #244와 연결된 구현 PR #247
