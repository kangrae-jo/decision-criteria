# 테스트 전략과 계층별 책임

- 상태: `adopted`
- 주제: 테스트 피라미드와 검증 범위
- 구현 예시: [방탈출 예약 대기 테스트 코드](https://github.com/kangrae-jo/spring-roomescape-waiting/tree/356fad7de9f3a1bf40e3819e314c51a6245fd36e/src/test)

## 결론

**유닛 테스트를 가장 많이 두는 피라미드형 구성을 지향한다.** 비즈니스 로직 테스트는 주요 유스케이스에 두고 E2E(End-to-End) 테스트는 대표 사용자 흐름에 둔다. 검증 범위가 넓어질수록 실행과 유지 비용을 고려해 사례를 줄인다. [Mike Cohn의 테스트 자동화 피라미드](https://www.mountaingoatsoftware.com/agile/the-forgotten-layer-of-the-test-automation-pyramid)

```text
         / \            E2E 테스트 (소수)
        /___\
       /     \          비즈니스 로직 테스트 (선별)
      /_______\
     /         \        유닛 테스트 (다수)
    /___________\
```

## 유닛 테스트

개별 객체의 계산과 상태 전이를 검증한다. 다양한 입력과 경계값을 이 층에서 확인한다. 예를 들어 시각을 고정하고 미래 예약과 지난 예약의 취소 가능 여부를 확인한다.

## 비즈니스 로직 테스트

하나의 유스케이스를 실행해 성공과 실패 분기 및 객체 간 협력을 검증한다. 예를 들어 예약 취소에 대기자 승격이 포함되면 두 변경이 모두 반영되는지 확인한다.

- 저장소의 조회 결과에 따른 분기는 테스트 대역으로 검증한다.
- 쿼리와 제약은 실제 DB를 연결한 통합 테스트로 확인한다. DB 엔진에 의존하는 동작은 운영과 같은 엔진에서 검증한다.
- 롤백은 실제 DB를 연결한 상태에서 첫 저장 이후에 실패를 일으켜 앞선 변경이 되돌아갔는지 확인한다.

## E2E 테스트

외부 진입점부터 결과까지 이어지는 대표 흐름을 검증한다. 예를 들어 HTTP로 예약을 취소한 뒤 목록을 다시 조회해 변경이 반영됐는지 확인한다. 요청 바인딩과 오류 응답의 세부 조합은 웹 슬라이스에서 검증한다.

## 비중 조정

**같은 결함을 재현할 수 있는 가장 좁은 층을 선택한다.** E2E에서 발견한 결함을 하위 층에서 재현할 수 있으면 그곳에 회귀 테스트를 둔다. DB 제약과 트랜잭션에 위험이 집중된 기능은 통합 테스트 비중을 늘린다. [Ham Vocke의 테스트 배치 기준](https://martinfowler.com/articles/practical-test-pyramid.html#AvoidTestDuplication)

구성을 조정한 뒤 같은 환경에서 실행 시간과 간헐 실패 빈도를 비교한다. 옮긴 테스트가 기존에 발견하던 결함을 계속 잡는지도 확인한다.
