# 세션과 토큰 기반 인증 상태 선택

- 상태: draft
- 예시 기준: Setty server의 AuthService, AuthInterceptor, LoginMemberArgumentResolver, AuthServiceTest 정적 확인
- 주제: 인증 상태의 보관 위치와 검증 방식
- 선택: 동일 출처 웹은 세션, 모바일·외부 API는 짧은 만료의 Bearer 토큰을 기본으로 사용

## 결론

**채택: 동일 출처 웹은 서버 세션을 기본으로 하고, 모바일·외부 API는 짧은 만료의 Bearer 토큰을 기본으로 한다.** 클라이언트 특성, 즉시 무효화 요구, 인증 상태 저장 비용으로 선택한다.

**거부: 수평 확장만을 이유로 토큰을 선택한다.** 세션도 공유 저장소를 두면 여러 서버에서 검증할 수 있다. 토큰은 세션 저장소를 없애는 대신 만료·로그아웃·탈취 대응 정책을 추가한다.

**채택: 토큰에는 식별자와 만료처럼 안정적인 최소 정보만 넣는다.** 현재 권한이 즉시 반영돼야 하는 자원 인가는 서버의 현재 정책을 최종 기준으로 삼는다.

## 빠른 기준

| 질문 | 판단 |
| --- | --- |
| 동일 출처 브라우저가 주 클라이언트이고 강제 로그아웃·동시 로그인 제어가 중요한가? | 서버 세션 |
| 모바일 앱·외부 API가 요청마다 인증 정보를 명시적으로 붙여야 하는가? | 짧은 만료의 Bearer 토큰 |
| 서버를 여러 대로 늘리는가? | 세션 공유 저장소 비용과 토큰 무효화 비용을 비교. 이것만으로 결정하지 않음 |
| 계정 비활성화·권한 변경을 즉시 반영해야 하는가? | 세션 또는 토큰 무효화 저장소·현재 권한 조회 필요 |
| 토큰이 서버 DB에서 식별자를 조회해야만 유효한가? | 불투명 토큰. 상태 보관 비용은 세션과 같은 축에서 판단 |
| 역할을 토큰 claim으로 넣는가? | 빠른 1차 판별까지만 허용. 최종 자원 인가는 현재 서버 정책으로 확인 |

## 1. 적용 범위

이 기준은 인증 상태를 서버 세션에 둘지, 클라이언트가 제시하는 토큰으로 검증할지를 다룬다.

포함:

- 인증 상태의 보관·검증 주체
- 로그아웃, 만료, 강제 차단, 동시 로그인
- 수평 확장 시 추가되는 상태 관리 비용
- 토큰 claim과 현재 권한의 정합성

비범위:

- 인증 정보를 Cookie와 Authorization 헤더 중 어디로 보낼지
- 예약·매장처럼 특정 자원에 대한 인가 규칙
- Spring Security 도입 여부

인증 정보의 전달 위치는 [Cookie와 Authorization 헤더의 인증 정보 전달 선택](cookie-vs-authorization-header.md)에서 다룬다.

## 2. 두 방식의 차이

| 항목 | 서버 세션 | 자체 검증 가능한 토큰 |
| --- | --- | --- |
| 인증 상태의 원본 | 서버 세션 저장소 | 서명된 토큰의 claim과 만료 |
| 요청 검증 | 세션 ID로 서버 상태 조회 | 서명·만료 검증 |
| 로그아웃·강제 차단 | 세션 삭제로 즉시 반영 | 만료 대기 또는 무효화 목록·토큰 버전 필요 |
| 동시 로그인 제한 | 사용자별 세션 목록을 서버에서 관리 | 별도 상태를 추가해야 함 |
| 서버 확장 | 공유 세션 저장소 또는 고정 라우팅 필요 | 서명 키 배포와 토큰 수명 관리 필요 |
| 주요 비용 | 세션 저장소 운영과 조회 | 탈취 대응, 짧은 만료, 재발급·무효화 정책 |

자체 검증 가능한 토큰은 여기서 서명된 access token을 뜻한다. 불투명 토큰처럼 서버가 토큰을 조회해야만 하는 구조는 상태를 서버에 둔다. 이름이 토큰이어도 세션과 같은 비용 축에서 판단한다.

JWT가 서명된 JWS라면 claim 위조는 서명 검증에서 실패한다. 그러나 서명은 기밀성을 보장하지 않는다. 암호화된 JWE가 아닌 일반 JWT claim은 읽을 수 있으므로 비밀번호·개인정보·권한 변경 이력 같은 민감한 값을 넣지 않는다.

## 3. Setty 예시: 서버 상태를 가진 불투명 Bearer 토큰

Setty의 플랫폼 회원 인증은 자체 검증 JWT가 아니다. AuthService가 로그인 성공 때 UUID를 만들고 Member.rotateToken으로 회원의 token 컬럼을 갱신한다. AuthInterceptor는 Authorization 헤더의 Bearer 값을 MemberRepository.findByToken으로 조회해 인증한다.

~~~text
로그인 성공
→ AuthService: UUID 생성
→ Member.token: 새 UUID로 교체
→ 요청: Authorization Bearer {UUID}
→ AuthInterceptor: findByToken으로 현재 회원 조회
~~~

이 토큰은 클라이언트가 값을 전달하지만 인증 상태의 원본은 DB다. 따라서 이 기준에서는 서버 세션과 같은 상태 관리 축에서 판단한다.

- 로그아웃은 AuthService.logout의 Member.clearToken으로 즉시 무효화된다.
- Member에는 token 컬럼 하나만 있으므로 새 로그인은 기존 플랫폼 회원 토큰을 교체한다.
- 보호 요청마다 token 조회가 발생한다. DB 조회 비용과 서버 상태 저장 비용이 든다.
- 정적 확인한 코드에는 token 만료 시각이 없다. 장기 탈취 대응과 만료 정책은 확인 필요다.

반대로 서명된 access token을 선택하면 서버는 서명·만료로 요청 주체를 확인할 수 있다. 로그아웃을 클라이언트 삭제만으로 끝내면 탈취된 토큰은 만료 전까지 사용할 수 있다. 즉시 무효화가 필요하면 짧은 access token, 재발급 수단, 토큰 버전 또는 무효화 저장소를 함께 설계한다. 무효화 저장소를 둔 토큰은 완전한 무상태 구조가 아니다.

## 4. 역할 claim과 DB 조회

인증은 요청 주체가 누구인지 확인한다. 인가는 그 주체가 현재 자원에 접근할 수 있는지 확인한다. 두 판단의 최신성 요구는 다를 수 있다.

| 상황 | 판단 |
| --- | --- |
| memberId 확인 | 서명·만료가 유효한 토큰 claim 사용 가능 |
| 관리자 경로의 빠른 진입 차단 | role claim의 1차 판별 허용 |
| 역할 변경·계정 정지 직후의 요청 | DB 또는 권한 캐시를 최종 기준으로 확인 |
| 매장 예약처럼 자원 소유 관계 확인 | Service 또는 권한 조건을 포함한 조회에서 확인 |

**거부: role claim만으로 모든 인가를 끝낸다.** 토큰 발급 뒤 role이 변경돼도 기존 claim은 만료 전까지 바뀌지 않는다. 역할 변경을 즉시 반영하지 않아도 되는 짧은 수명 토큰이라는 정책이 명시된 경우에만 최종 판단으로 사용한다.

DB 조회 비용은 무시할 비용이라고 단정하지 않는다. 회원 ID의 단건 조회가 병목인지, 권한 최신성이 필요한지를 SQL 횟수·지연 시간·트래픽으로 측정한다. 최신 권한이 필요하다면 조회 비용은 인가 규칙의 비용이다.

Setty는 token에 role claim을 넣지 않는다. AuthInterceptor가 MemberRepository.findByToken으로 현재 Member를 조회하고, LoginMemberArgumentResolver는 request attribute의 Member를 그대로 반환한다. 따라서 Resolver에서 조회를 반복하지는 않지만 보호 요청마다 Interceptor의 DB 조회가 발생한다.

Member의 role은 현재 DB 행에 있다. 이 조회가 role 변경을 모든 인가 규칙에 즉시 반영하는지는 각 Service·Controller의 role 사용 여부를 추가로 확인해야 한다.

## 5. 공통 처리 경계

인증 방식이 달라도 컨트롤러는 인증 정보를 직접 파싱하지 않는다.

1. Interceptor가 세션 ID 또는 토큰을 검증한다.
2. 검증된 인증 주체를 요청 범위에 둔다.
3. ArgumentResolver가 필요할 때 LoginMember를 제공한다.
4. Service가 자원 소유·매장 관계 같은 인가를 판단한다.

Setty는 AuthInterceptor가 DB에서 조회한 Member를 request attribute에 저장하고, LoginMemberArgumentResolver가 이를 Controller에 제공한다. 이 경계는 컨트롤러의 token 파싱과 Repository 조회 중복을 막는다.

## 6. 검증 방법

- 세션이 없거나 삭제된 요청이 401인지 확인한다.
- 세션 삭제 뒤 같은 sessionId가 다시 인증되지 않는지 확인한다.
- Bearer 토큰의 누락, 형식 오류, 서명 오류, 만료가 모두 401인지 확인한다.
- 계정 비활성화 또는 role 하향 직후의 요청이 선택한 정책대로 차단되는지 확인한다.
- 다중 서버 환경이면 서로 다른 서버에서 같은 세션 또는 토큰이 검증되는지 확인한다.
- 요청당 Member 조회 수와 p95 지연 시간을 측정해 권한 최신성의 비용을 기록한다.
- Setty의 AuthServiceTest처럼 로그아웃 뒤 기존 token 조회가 실패하는지 확인한다.
- Setty의 ListingApiTest처럼 Bearer token 누락·잘못된 token이 401인지 확인한다.

## 최종 판단 기준

> 인증 방식은 웹·모바일이라는 이름이나 수평 확장만으로 고르지 않는다. 즉시 무효화와 서버 상태 관리가 중요하면 세션을, 다양한 클라이언트의 명시적 요청 인증이 중요하면 짧은 만료의 Bearer 토큰을 선택한다. 토큰 claim은 발급 시점의 정보이며, 최신 권한이 필요한 인가는 서버의 현재 정책으로 확인한다.

## 검증 범위

- 확인됨: Setty의 UUID token 발급·교체, DB token 조회, 로그아웃 무효화, request attribute 기반 LoginMember 주입
- 확인 필요: token 만료 정책, 다중 서버 운영 방식, role 변경과 자원 인가의 정합성
- 비범위: Cookie·헤더 전달 위치, 자원별 인가 정책
