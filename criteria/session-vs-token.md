# 세션과 토큰 기반 인증 상태 선택

- 상태: draft
- 주제: 인증 상태의 보관 위치와 검증 방식
- 판단 축: 즉시 무효화, 서버 상태 저장, 요청당 조회, 클라이언트 종류, 권한 최신성

## 결론

**채택: 즉시 무효화와 로그인 상태 제어가 중요하면 서버 세션 또는 불투명 토큰을 선택한다.** 여러 서버가 저장소 조회 없이 인증해야 하고 발급 이후의 정보 지연을 허용할 수 있으면 짧은 수명의 자체 검증 토큰을 선택한다.

**거부: 세션은 과거 방식이고 토큰은 최신 방식이라는 구분.** 수평 확장과 모바일 지원만으로 자체 검증 토큰을 선택하지 않는다.

**채택: 자체 검증 토큰에는 식별자와 만료처럼 안정적인 최소 정보만 넣는다.** 현재 권한이 즉시 반영돼야 하는 자원 인가는 서버의 현재 정책을 최종 기준으로 삼는다.

## 빠른 기준

| 질문 | 판단 |
| --- | --- |
| 브라우저 중심이며 강제 로그아웃·동시 로그인 제어가 중요한가? | 서버 세션 |
| API 클라이언트가 토큰을 명시적으로 전달하면서 즉시 무효화도 필요한가? | 불투명 토큰 |
| 여러 서버가 인증 저장소 조회 없이 요청을 검증해야 하는가? | 짧은 수명의 자체 검증 토큰 |
| 권한 변경을 즉시 반영해야 하는가? | 서버 상태 조회 또는 별도 무효화 정책 |
| 서버를 여러 대로 늘리는가? | 세션 공유 비용과 토큰 무효화 비용을 비교. 이것만으로 결정하지 않음 |
| 역할을 토큰 claim으로 넣는가? | 정보 지연을 허용할 때만 사용. 자원 인가는 현재 서버 정책 우선 |

## 1. 적용 범위

이 기준은 인증 상태를 서버 세션에 둘지, 클라이언트가 제시하는 토큰으로 검증할지를 다룬다.

포함:

- 인증 상태의 보관·검증 주체
- 로그아웃, 만료, 강제 차단, 동시 로그인
- 수평 확장 시 추가되는 상태 관리 비용
- 토큰 claim과 현재 권한의 정합성

비범위:

- 인증 정보를 Cookie와 Authorization 헤더 중 어디로 보낼지
- 예약·매장처럼 특정 자원에 대한 인가 규칙
- Spring Security 도입 여부

인증 정보의 전달 위치는 [Cookie와 Authorization 헤더의 인증 정보 전달 선택](cookie-vs-authorization-header.md)에서 다룬다.

## 2. 방식별 차이

| 항목 | 서버 세션 | 불투명 토큰 | 자체 검증 토큰 |
| --- | --- | --- | --- |
| 인증 상태의 원본 | 세션 저장소 | DB·Redis의 토큰 레코드 | 서명된 claim과 만료 |
| 요청 검증 | 세션 ID 조회 | 토큰 조회 | 서명·만료 검증 |
| 즉시 무효화 | 세션 삭제 | 토큰 삭제·폐기 | 별도 무효화 상태가 없으면 어려움 |
| 동시 로그인 제한 | 세션 목록으로 제어 | 사용자별 토큰 레코드로 제어 | 별도 상태 필요 |
| 서버 확장 | 공유 세션 저장소 필요 | 공유 토큰 저장소 필요 | 서명 키와 검증 정책 공유 |
| 주요 비용 | 세션 저장소 운영 | 요청당 조회와 토큰 저장소 운영 | 탈취 대응, 짧은 만료, 재발급 정책 |

불투명 토큰은 클라이언트가 의미를 해석할 수 없는 임의 문자열이다. 서버가 저장소를 조회해야 하므로 이름은 토큰이어도 상태 관리 비용은 세션과 같다.

자체 검증 토큰은 여기서 서명된 access token을 뜻한다. 서버는 저장소 조회 없이 claim과 만료를 검증할 수 있다.

JWT가 서명된 JWS라면 claim 위조는 서명 검증에서 실패한다. 그러나 서명은 기밀성을 보장하지 않는다. 암호화된 JWE가 아닌 일반 JWT claim은 읽을 수 있으므로 비밀번호·개인정보·권한 변경 이력 같은 민감한 값을 넣지 않는다.

## 3. 방식별 선택 기준

### 서버 세션

다음 조건이면 선택한다.

- 동일 출처 브라우저가 주 클라이언트다.
- 로그아웃, 계정 차단, 동시 로그인 제한을 서버에서 즉시 제어해야 한다.
- 공유 세션 저장소의 운영 비용을 감당할 수 있다.

세션 저장소를 공유하지 못하는 다중 서버 환경에서 고정 라우팅에만 의존해야 한다면 기본 선택으로 두지 않는다.

### 불투명 토큰

다음 조건이면 선택한다.

- 모바일·외부 API가 토큰을 명시적으로 전달해야 한다.
- 토큰 형식에 회원 정보와 권한을 노출하고 싶지 않다.
- 즉시 로그아웃과 서버 주도의 무효화가 필요하다.
- 요청당 토큰 저장소 조회 비용을 허용할 수 있다.

토큰을 사용자 행 하나에 직접 저장하면 기기별 로그인과 여러 세션 관리가 어려워진다. 여러 기기를 지원하면 별도 토큰 레코드와 만료 시각을 둔다.

### 자체 검증 토큰

다음 조건이면 선택한다.

- 여러 API 서버가 인증 저장소 조회 없이 요청을 검증해야 한다.
- 모바일·외부 서비스 등 여러 클라이언트가 같은 인증 계약을 사용한다.
- 짧은 만료 시간 동안 권한 정보가 늦게 반영되는 것을 허용할 수 있다.
- 키 교체, 재발급, 탈취 대응 정책을 운영할 수 있다.

즉시 무효화를 위해 모든 요청에서 무효화 저장소를 조회해야 한다면 무상태 이점이 줄어든다. 이 경우 불투명 토큰 또는 세션과 다시 비교한다.

## 4. 역할 claim과 DB 조회

인증은 요청 주체가 누구인지 확인한다. 인가는 그 주체가 현재 자원에 접근할 수 있는지 확인한다. 두 판단의 최신성 요구는 다를 수 있다.

| 상황 | 판단 |
| --- | --- |
| memberId 확인 | 서명·만료가 유효한 토큰 claim 사용 가능 |
| 관리자 경로의 빠른 진입 차단 | role claim의 1차 판별 허용 |
| 역할 변경·계정 정지 직후의 요청 | DB 또는 권한 캐시를 최종 기준으로 확인 |
| 매장 예약처럼 자원 소유 관계 확인 | Service 또는 권한 조건을 포함한 조회에서 확인 |

**거부: role claim만으로 모든 인가를 끝낸다.** 토큰 발급 뒤 role이 변경돼도 기존 claim은 만료 전까지 바뀌지 않는다. 역할 변경을 즉시 반영하지 않아도 되는 짧은 수명 토큰이라는 정책이 명시된 경우에만 최종 판단으로 사용한다.

DB 조회 비용은 무시할 비용이라고 단정하지 않는다. 회원 ID의 단건 조회가 병목인지, 권한 최신성이 필요한지를 SQL 횟수·지연 시간·트래픽으로 측정한다. 최신 권한이 필요하다면 조회 비용은 인가 규칙의 비용이다.

## 5. 공통 처리 경계

인증 방식이 달라도 컨트롤러는 인증 정보를 직접 파싱하지 않는다.

1. Interceptor가 세션 ID 또는 토큰을 검증한다.
2. 검증된 인증 주체를 요청 범위에 둔다.
3. ArgumentResolver가 필요할 때 LoginMember를 제공한다.
4. Service가 자원 소유·매장 관계 같은 인가를 판단한다.

인증 구현은 세션과 토큰을 LoginMember 같은 공통 인증 주체로 변환한다. 이 경계는 컨트롤러의 인증 정보 파싱과 Repository 조회 중복을 막는다.

## 6. 검증 방법

- 세션이 없거나 삭제된 요청이 401인지 확인한다.
- 세션 삭제 뒤 같은 sessionId가 다시 인증되지 않는지 확인한다.
- 인증 정보의 누락과 형식 오류가 401인지 확인한다.
- 계정 비활성화 또는 role 하향 직후의 요청이 선택한 정책대로 차단되는지 확인한다.
- 다중 서버 환경이면 서로 다른 서버에서 같은 세션 또는 토큰이 검증되는지 확인한다.
- 요청당 Member 조회 수와 p95 지연 시간을 측정해 권한 최신성의 비용을 기록한다.
- 불투명 토큰은 로그아웃·만료 뒤 같은 token으로 인증되지 않는지 확인한다.
- 자체 검증 토큰은 서명 오류, 만료, 키 교체와 재발급 흐름을 확인한다.

## 최종 판단 기준

> 인증 방식은 웹·모바일이라는 이름이나 수평 확장만으로 고르지 않는다. 브라우저 중심이며 서버가 로그인 상태를 제어해야 하면 세션을, API에서 토큰을 전달하면서 즉시 무효화해야 하면 불투명 토큰을, 저장소 조회 없는 분산 검증과 정보 지연을 허용하면 짧은 수명의 자체 검증 토큰을 선택한다.

## 검증 범위

- 확인 필요: 적용 서비스의 클라이언트 종류, 인증 트래픽, 무효화 시간 요구사항, 다중 서버 운영 방식
- 비범위: Cookie·헤더 전달 위치, 자원별 인가 정책
