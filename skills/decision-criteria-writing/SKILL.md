# 판단 기준 작성

## 목적

특정 기술을 소개하거나 하나의 프로젝트 선택을 정당화하는 글이 아니라, 여러 프로젝트에서 다시 사용할 수 있는 다음 형태의 기준을 만든다.

> 어떤 조건에서 무엇을 선택하고, 무엇을 거부하며, 어떤 비용을 감수하는가?

특정 시스템에 기준을 적용해 실제 선택을 기록하는 ADR과 구분한다.

## 먼저 읽을 자료

- 작업 시작 시 저장소 루트의 `README.md`에서 운영 규칙, 예시 사용 원칙과 문서 상태 정의를 읽는다. 이를 단일 진실원으로 따른다.
- 새 문서를 만들기 전에 `criteria/`에서 같은 판단 주제나 인접한 기준이 있는지 찾는다.
- 새 기준을 작성하거나 문서 구조를 크게 바꿀 때는 [선호 문서에서 추출한 작성 원칙](references/preferred-patterns.md)을 읽는다.
- 새 문서의 뼈대가 필요할 때만 [판단 기준 문서 골격](references/document-shape.md)을 읽는다. 기존 문서의 제한된 수정에는 일괄 적용하지 않는다.

## 판단을 만드는 순서

1. **판단 질문을 하나로 제한한다.** 제목이 `어떤 조건에서 A와 B 중 무엇을 선택하는가`에 답할 수 있어야 한다.
2. **결정 수준을 구분한다.** 아키텍처 스타일, 전달·상태 모델, 패턴, 제품, 세부 구현을 한 문서에서 연쇄적으로 확정하지 않는다.
3. **요구사항을 질문으로 바꾼다.** 즉시 결과, 상태 소유권, 실패 허용, 재처리, 최신성, 운영 능력처럼 선택을 바꾸는 축만 남긴다.
4. **가장 단순한 기본값을 정한다.** 복잡한 대안을 도입해야 할 조건과 기본값을 유지할 조건을 함께 쓴다.
5. **선택·거부·보류 조건을 확정한다.** 일반적인 장단점 목록에서 끝내지 않고 조건이 판단으로 이어지게 한다.
6. **얻는 것과 부담하는 것을 연결한다.** 장점과 비용을 서로 대응시키고, 예외와 운영 제약을 기록한다.
7. **기술적 전제와 검증 방법을 분리한다.** 미확인 내용은 `확인 필요`로 표시하고 결론을 지탱하는 사실을 검증할 방법을 쓴다.

결론을 정할 정보가 부족하면 특정 기술을 임의로 채택하지 않는다. 선택을 바꾸는 질문을 먼저 제시하거나 조건별 기준까지만 작성한다.

질문은 취향을 묻는 설문이 아니라 답에 따라 결론이 달라지는 분기여야 한다. 각 선택지가 어느 판단으로 이어지는지 함께 설명하고, 사용자가 이미 확정한 선호는 다시 묻지 않는다.

## 근거 사용

- 판단 근거는 요구사항, 기술적 전제와 트레이드오프에서 찾는다.
- 공식 명세와 기술 문서는 동작 전제를 확인하는 데 사용한다.
- 실험·측정은 성능, 장애 복구와 운영 비용처럼 환경에 따라 달라지는 전제를 확인한다.
- 코드·저장소·PR은 기준이 적용된 구현 예시로만 사용한다. 해당 구현의 채택 여부나 테스트 통과를 판단 근거 또는 독립 검증으로 사용하지 않는다.
- 블로그·영상·경험담은 판단 후보를 찾는 입력으로 사용할 수 있지만, 중요한 기술적 전제는 명세나 독립적인 측정으로 다시 확인한다.
- 확인한 사실과 그 원인에 대한 해석을 구분한다.

## 작성 규칙

- 결론을 먼저 쓰고 핵심 판단에 `채택`, `거부`, `유지`, `보류`, `비범위`를 명시한다.
- `빠른 기준`은 선택을 바꾸는 질문과 그 결과가 바로 연결되는 표로 작성한다.
- 이름, 유행, 팀의 막연한 친숙도보다 동작 특성과 요구사항을 기준으로 비교한다.
- 비슷해 보이는 개념은 먼저 정의하고 비교한다. 서로 다른 결정이면 문서를 나누고 링크한다.
- 하나의 질문만으로 결정할 수 없다면 필요한 질문의 조합과 판단 순서를 명시한다.
- 대안마다 채택 조건, 얻는 것, 비용과 제약을 함께 쓴다.
- 기본값과 예외의 우선순위를 모호하게 두지 않는다.
- 구현 예시는 기준을 설명한 뒤에 배치한다. 예시가 없어도 판단 기준은 완성될 수 있다.
- 배경 설명과 용어 목록은 결론을 이해하거나 선택을 바꾸는 데 필요한 만큼만 남긴다.
- 인접 문서와 중복되는 상세 내용은 삭제하고 해당 문서에 링크한다.
- 모든 후보를 같은 비중으로 설명하지 않는다. 실제로 선택을 가르는 대안과 사용자가 확정한 선호에 분량을 배분한다.

## 문서 구성

다음 요소는 기본적으로 포함한다.

- 제목과 `상태`, `주제`; 필요하면 `선택`, `검토일`
- 결론
- 빠른 기준
- 판단 순서 또는 대안별 채택 조건
- 트레이드오프나 비용·제약
- 검증 방법 또는 검증 범위
- 한 문단의 최종 판단 기준

적용 범위·비범위, 개념 비교, 구현 예시, 관련 판단 기준, 기술 문서는 판단에 필요할 때만 추가한다. 모든 문서에 같은 목차를 강제하지 않는다.

새 기준을 추가하면 루트 `README.md`의 기준 목록에서 적절한 분야에 연결한다. 공통 개념을 여러 문서에 반복해야 한다면 `references/`에 단일 진실원으로 분리하고 링크한다.

## 완료 점검

- 문서 하나가 하나의 판단 질문만 다루는가?
- 빠른 기준만 읽어도 조건별 선택이 가능한가?
- 기본값, 대안 도입 조건과 거부 조건이 구분되는가?
- 장점뿐 아니라 비용·제약과 예외가 있는가?
- 구현 예시가 판단 근거나 검증 자료로 둔갑하지 않았는가?
- 인접 판단과 범위가 겹치지 않으며 필요한 링크가 있는가?
- 상태가 루트 `README.md` 정의와 일치하는가?
- 미확인 사실이 `확인 필요`로 남아 있는가?
- 검증 항목이 단순한 구현 예시 확인이 아니라 기술적 전제를 확인하는가?
- 최종 판단 기준이 문서 전체의 결론을 독립적으로 요약하는가?
