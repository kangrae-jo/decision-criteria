1. `criteria/abstract-class-vs-interface.md`

나머지 판단 기준도 채택된 내용으로 존중하지만, 문서 구조와 판단 전개가 충돌하면 위 세 문서의 방식을 우선한다. 다른 문서에서는 상태 관리, 기술 문서 연결, 검증 방법과 도메인별 세부 패턴을 보완한다.

## 세 문서에서 우선 적용할 패턴

| 기준 문서 | 강하게 반영할 패턴 | 적용 방법 |
| --- | --- | --- |
| 추상 클래스와 인터페이스 선택 | 선택지 비교 전에 관계 자체의 타당성을 확인 | `A와 B 중 무엇인가`보다 `이 선택이 필요한가`를 첫 질문으로 둔다 |
| 세션과 토큰 기반 인증 상태 선택 | 용어를 세분화하고 적용 범위와 인접 결정을 분리 | 이름이 같은 후보도 상태 원본, 검증, 최신성처럼 실제 동작으로 다시 나눈다 |
| 비동기 메시지 전달 방식 선택 | 모델을 제품보다 먼저 결정하고 질문 조합으로 분기 | 동기·알림·작업 큐·스트림 같은 전달 모델을 정한 뒤 제품 선택 문서로 넘긴다 |

### 1. 판단의 전제부터 검증

`추상 클래스와 인터페이스 선택`은 공통 코드가 있다는 이유로 두 구현 수단부터 비교하지 않는다. 먼저 자연스러운 상위 타입 관계인지 묻고, 그 관계가 성립할 때만 상태·불변식과 행위 계약을 비교한다.

이 구조를 일반화한다.

```text
문제가 실제로 존재하는가?
→ 이 결정 수준에서 해결해야 하는가?
→ 기본 수단으로 충분한가?
→ 추가 조건이 있을 때만 복잡한 대안을 선택
```

중복 제거, 최신 기술, 확장 가능성 같은 추상적인 이유만으로 복잡한 대안을 채택하지 않는다. 조합, 동기 호출, 기존 상태 원본처럼 단순한 기본값을 먼저 검토한다.

### 2. 선택지는 이름이 아니라 동작으로 구분

`세션과 토큰 기반 인증 상태 선택`은 토큰을 하나로 다루지 않고 불투명 토큰과 자체 검증 토큰을 나눈다. 이름은 모두 토큰이지만 상태 원본, 요청당 조회, 즉시 무효화와 정보 최신성이 다르기 때문이다.

후보를 나눌 때 다음을 확인한다.

- 상태나 데이터의 원본이 어디에 있는가?
- 누가 검증하고 누가 최종 권한을 가지는가?
- 변경이 언제 반영되는가?
- 실패와 복구를 누가 책임지는가?
- 분산·확장 시 어떤 상태와 운영 비용이 새로 생기는가?

인접한 결정은 비범위로 둔다. 예를 들어 인증 상태 보관과 Cookie·Authorization 헤더 전달은 연결되지만 같은 판단이 아니다.

### 3. 구현 제품보다 문제 해결 모델을 먼저 선택

`비동기 메시지 전달 방식 선택`은 Kafka와 RabbitMQ를 바로 비교하지 않는다. 즉시 결과, 누락 허용, 단일 작업자 처리, 기록 보존과 독립 소비 여부로 전달 모델을 먼저 정한다.

다음 순서를 우선한다.

```text
요구사항과 실패 허용 범위
→ 동기·비동기, 상태·전달 모델
→ 패턴과 책임 경계
→ 제품
→ 세부 설정
```

상위 결정이 다른 문서에 이미 있으면 링크하고 현재 문서는 한 단계만 다룬다.

### 4. 빠른 기준은 작은 의사결정 트리

빠른 기준 표는 기능 비교표가 아니다. 각 행은 답에 따라 선택이 달라지는 질문이어야 한다.

- 질문은 서로 다른 판단 축을 다룬다.
- 답은 `지원`, `좋음`이 아니라 선택·유지·재검토 같은 행동으로 끝낸다.
- 질문 하나만으로 결론이 나지 않으면 조합해야 한다고 명시한다.
- 가장 강한 제외 조건이나 기본값 확인 질문을 앞에 둔다.

### 5. 채택 사례와 거부 사례를 함께 사용

좋은 기준은 적합한 사례뿐 아니라 비슷해 보이지만 거부하는 사례도 설명한다.

- 채택 사례: 어떤 조건이 기준을 충족했는지 보여준다.
- 거부 사례: 흔한 오해나 잘못된 판단 축을 드러낸다.
- 결합 사례: 두 대안이 배타적이지 않을 때 책임 경계를 보여준다.
- 보류 사례: 현재 요구보다 앞선 추상화나 운영 복잡도를 미룬다.

사례는 기준을 설명하기 위한 것이며, 사례가 존재한다는 사실이 기준의 근거는 아니다.

## 저장소 전체에서 보완할 패턴

- 결론은 문서 첫 부분에 둔다.
- 기술적 사실, 사용자 선택과 미확인 추측을 구분한다.
- 세 개 이상의 대안을 반복 축으로 비교하면 표를 사용한다.
- 성능과 운영 특성은 동일 조건의 실험·측정으로 검증한다.
- 독립적인 공식 명세로 확인한 전제와 구현 저장소에서 관찰한 동작을 구분한다.
- 관련 기준을 링크해 단일 진실원을 유지한다.
- 마지막 인용문은 기본값, 대안 조건과 핵심 제약을 함께 요약한다.

## 피할 문서 형태

- 기술의 정의와 장단점만 나열하고 선택 조건이 없는 글
- `A는 구식, B는 최신`처럼 유행으로 결론 내리는 글
- 모든 선택지를 같은 비중으로 소개해 기본값을 알 수 없는 글
- 제품, 패턴, 아키텍처 스타일과 세부 설정을 한 번에 결정하는 글
- 저장소나 PR이 사용한 기술을 그대로 근거로 채택하는 글
- 검증하지 않은 성능 우열이나 내부 동작을 사실로 단정하는 글
- 인접 기준의 설명을 복사해 범위와 문서 길이를 늘리는 글
- 미래 가능성만으로 추상화나 운영 구성요소를 미리 추가하는 글
